## Шаги

### `order` Заказ Анны

`user → server` · `legit`
Сообщение: новый заказ · Итог: заказ № 1002

```http
POST /orders
Cookie: session=…анна…
```

#### Просто

Анна покупает в интернет-магазине чайник. Магазин сохраняет заказ и даёт ему **номер 1002**. В
заказе её имя, адрес доставки и телефон.

#### По шагам

Браузер Анны отправляет заказ вместе с кукой сессии: так сервер знает, что это она. Сервер
записывает заказ в таблицу `orders` и запоминает, чей он.

#### Глубже

Номера заказов идут подряд: 1001, 1002, 1003. Это удобно магазину, но значит, что соседние номера
легко угадать. Само по себе это ещё не ошибка: всё решит то, как сервер выдаёт заказ по номеру.

### `own` Свой заказ

`attacker → server` · `legit`
Сообщение: GET /orders/1001 · Итог: свой заказ

```http
GET /orders/1001
Cookie: session=…атакующий…
```

#### Просто

У атакующего тоже есть аккаунт в магазине, и он купил что-то дешёвое. Его заказ — **1001**.
Открывая его, он видит номер прямо в адресе страницы.

#### По шагам

Браузер просит страницу `/orders/1001`. Сервер показывает заказ: всё честно, заказ его.

#### Глубже

Атакующий здесь не взламывает вход: он обычный покупатель со своим паролем и своей сессией.
Поэтому проверка входа на сайте его пропускает. Вопрос в другом — проверяет ли сервер, **чей**
заказ просят показать.

### `swap` Другой номер

`attacker → server` · `attack`
Сообщение: GET /orders/1002 · Итог: принято

```http
GET /orders/⟦1002⟧
Cookie: session=…атакующий…
```

#### Просто

Атакующий меняет в адресе одну цифру: вместо 1001 пишет **1002**. Это заказ Анны, но атакующий
этого не знает — ему просто интересно, что там.

#### По шагам

Сессия та же — атакующего. Изменён только номер в адресе. Для сервера это обычный запрос
вошедшего покупателя.

#### Глубже

Номер в адресе — прямая ссылка на запись в базе (*direct object reference*). Всё, что пришло из
браузера, атакующий может поменять: адрес, поля формы, тело запроса к API. Отсюда и название
ошибки: IDOR, небезопасная прямая ссылка на объект.

### `lookup` Поиск только по номеру

`server → db` · `attack` · `without-defence`
Сообщение: SELECT ... id = 1002 · Итог: атака

```sql
SELECT * FROM orders
WHERE id = ⟦1002⟧
```

#### Просто

Сервер проверил, что посетитель вошёл, и сразу ищет заказ **по одному номеру**. Чей это заказ, он
не спрашивает.

#### По шагам

Сервер берёт номер из адреса и подставляет его в запрос к базе. Запрос безопасен от инъекции,
но в нём нет условия «заказ принадлежит тому, кто спрашивает».

#### Глубже

Вход (кто ты) проверен, а авторизация (что тебе можно) — нет. В каталоге MITRE это CWE-639
«Authorization Bypass Through User-Controlled Key»: обход проверки прав через ключ, которым
управляет пользователь. Там же названы другие имена этой ошибки: IDOR и BOLA.

### `leak` Чужой заказ

`server → attacker` · `attack` · `without-defence`
Сообщение: заказ 1002 Анны · Итог: чужие данные утекли

```text
Заказ 1002
Получатель: Анна
Адрес и телефон: …
```

#### Просто

Сервер показывает атакующему **заказ Анны**: имя, адрес, телефон. Анна об этом не узнает.

#### По шагам

База нашла заказ 1002, сервер отдал его целиком. Ни ошибки, ни предупреждения: для сервера всё
прошло как обычно.

#### Глубже

Перебирая номера подряд, так можно выкачать все заказы магазина. Та же ошибка на запросах,
которые меняют данные, даёт править или отменять чужие заказы. В OWASP Top 10:2021 это пункт A01
«Broken Access Control», он поднялся туда с пятого места; просмотр чужой записи по её номеру
назван в нём прямо.

### `owner` Поиск с владельцем

`server → db` · `attack` · `with-defence` · `stopped`
Сообщение: 1002 и владелец 77 · Итог: атака не сработала

```sql
SELECT * FROM orders
WHERE id = ⟦1002⟧
  AND owner_id = 77  -- из сессии
```

#### Просто

Теперь сервер спрашивает базу: найди заказ 1002, **но только если он принадлежит тому, кто
спрашивает**. Кто спрашивает, сервер знает по сессии, а не по адресу. Здесь атака и
останавливается.

#### По шагам

Номер заказа по-прежнему берётся из адреса. Но к нему добавлено второе условие: владелец — это
пользователь из сессии атакующего (у него номер 77). Подделать его через адрес нельзя.

#### Глубже

Это проверка доступа к объекту: при каждом запросе к записи сервер сверяет, что этому
пользователю её можно видеть или менять. OWASP советует делать это на сервере, для каждого
объекта и каждого запроса, одним общим механизмом, а не в каждом месте заново. Удобный приём —
искать запись не во всей таблице, а среди записей текущего пользователя.

### `notfound` Нет такого заказа

`server → attacker` · `safe` · `with-defence`
Сообщение: 404 Not Found · Итог: чужой заказ не показан

```http
HTTP/1.1 404 Not Found
```

#### Просто

База не нашла заказ 1002 **среди заказов атакующего**. Сервер отвечает: такого заказа нет.
Данные Анны остались закрытыми.

#### По шагам

Сервер возвращает 404. Атакующий не узнаёт даже, есть ли заказ с таким номером у кого-то другого.

#### Глубже

Можно ответить и 403 Forbidden («нельзя»). Но стандарт HTTP (RFC 9110, раздел 15.5.4) разрешает
серверу, который хочет скрыть само существование запретного ресурса, отвечать 404. Так перебор
номеров ничего не подсказывает. Сам отказ стоит записать в журнал: много отказов подряд от одного
пользователя похожи на перебор.

## Как защититься

- **Проверка владельца на каждом запросе.** Сервер сверяет, что запись принадлежит тому, кто
  вошёл, или что у него есть права на неё. Для чтения, изменения и удаления — всегда. Это главная
  защита.
- **Пользователь берётся из сессии.** Кто спрашивает, сервер узнаёт по своей сессии, а не по
  номеру или имени в адресе, форме или теле запроса.
- **Одна общая проверка.** Правила доступа задаются в одном месте и действуют везде, а по
  умолчанию доступ закрыт.
- **Случайные номера не лечат.** Длинные случайные идентификаторы (например, UUID) труднее
  угадать, но номер может утечь через ссылку или журнал. OWASP считает их только дополнительным
  слоем, а не заменой проверки.
- **Тесты на чужой доступ.** Автотест входит под одним пользователем и просит запись другого:
  ответ должен быть отказом.
- **Журнал отказов.** Отказы в доступе записываются, частые отказы от одного пользователя
  поднимают тревогу.
