## Шаги

### `form` Форма входа

`attacker → server` · `legit`
Сообщение: GET /login · Итог: страница входа

```http
POST /login
login=...&password=...
```

#### Просто

Атакующий открывает страницу входа в интернет-магазин. Пока ничего плохого: так делает любой
посетитель.

#### По шагам

Браузер запрашивает страницу `/login`. Сервер отдаёт форму с двумя полями: «Логин» и «Пароль».

#### Глубже

Форма отправит запрос `POST /login` с полями `login` и `password`. Сервер вставит их в запрос
к таблице `users` на языке SQL — языке, на котором сайт задаёт вопросы базе данных.

Пример упрощён: пароль сравнивается прямо в запросе. Настоящие сайты хранят не сам пароль, а его
хеш, но для инъекции это неважно: логин в запрос попадает всё равно.

### `trick` Хитрый логин

`attacker → server` · `attack`
Сообщение: admin' -- · Итог: принято как текст

```http
POST /login
login=⟦admin' --⟧&password=123
```

#### Просто

В поле «Логин» он пишет `admin`, а после него кавычку и два дефиса. Человеку эти знаки ничего
не говорят. Но в языке запросов к базе у них **особый смысл**.

#### По шагам

В поле «Логин» уходит строка `admin' --`, пароль любой. Сервер принимает её как обычный текст.

#### Глубже

В SQL кавычка открывает и закрывает текстовое значение, а `--` начинает комментарий. Браузер
передаст кавычку и пробел в закодированном виде (`%27` и `+`), сервер раскодирует их обратно.
Сам по себе ввод ещё ничего не сделал: опасно то, как сервер с ним поступит дальше.

### `glue` Сервер склеивает запрос

`server → db` · `attack` · `without-defence`
Сообщение: SELECT ... · Итог: атака

```sql
SELECT * FROM users WHERE
login = '⟦admin' --⟧' AND password = '123'
```

#### Просто

Сервер берёт то, что ввёл посетитель, и **вклеивает прямо в вопрос к базе**. Кавычка из ввода
обрывает логин раньше времени, а два дефиса велят базе не читать дальше. Проверка пароля
оказывается вычеркнута.

#### По шагам

Сервер собирает запрос склейкой строк: кусок запроса, ввод посетителя, снова кусок запроса. Готовый
текст уходит в базу.

#### Глубже

Ввод стал частью кода запроса: это и есть ошибка CWE-89. Кавычка из ввода закрыла значение
`'admin'`. Дальше стоит `--`, и в большинстве баз данных это комментарий до конца строки. База
пропускает остаток строки: лишнюю кавычку и проверку `AND password = '123'`.

### `answer` База отвечает

`db → server` · `attack` · `without-defence`
Сообщение: запись admin · Итог: найдена без пароля

#### Просто

База честно выполняет то, что ей прислали: найти пользователя admin. Про пароль её никто не
спросил.

#### По шагам

База возвращает запись пользователя admin. Отличить задуманный запрос от испорченного она не
может: для неё это просто текст запроса.

#### Глубже

Без комментария база выполнила `SELECT * FROM users WHERE login = 'admin'`. Через ту же ошибку
можно и иначе менять запрос:

- добавить условие, которое всегда верно, и получить все строки таблицы;
- присоединить через `UNION` строки из другой таблицы;
- если сайт не показывает данные, узнавать их по косвенным признакам ответа (слепая инъекция).

### `enter` Вход без пароля

`server → attacker` · `attack` · `without-defence`
Сообщение: Привет, admin · Итог: вход выполнен

#### Просто

Сервер видит, что база нашла пользователя, и пускает атакующего под именем admin. Обычно это
администратор. Пароль атакующий так и не узнал: он не понадобился.

#### По шагам

Сервер считает вход успешным, создаёт сессию для admin и отдаёт личный кабинет.

#### Глубже

Итог — обход проверки входа. Та же ошибка в других местах сайта даёт читать и менять данные:
всё, к чему у сайта есть доступ в базе. Класс ошибки — CWE-89, в OWASP Top 10:2021 это пункт
A03 «Инъекции».

### `param` Запрос с параметром

`server → db` · `attack` · `with-defence` · `stopped`
Сообщение: параметр: admin' -- · Итог: ввод остался данными, атака не сработала

```sql
SELECT * FROM users WHERE
login = ? AND password = ?

параметр 1: ⟦admin' --⟧
параметр 2: 123
```

#### Просто

Теперь сервер отправляет базе вопрос и ответы посетителя **отдельно**, как бланк и то, что в него
вписали. Вредный ввод `admin' --` доходит до базы, но только как вписанное значение. Кавычка и
дефисы в нём — просто знаки, вопрос они не меняют. Здесь атака и останавливается.

#### По шагам

Сервер отправляет запрос с пустыми местами `?` и отдельно значения для них. Запрос не склеивается
с вводом, поэтому ввод не может стать его частью.

#### Глубже

Это параметризованный запрос (*prepared statement*, подготовленный запрос) — главная защита по
OWASP. Устройство запроса задано заранее, а значение попадает только в своё место и всегда
считается данными. Знак места в разных базах пишется по-разному: `?`, `$1`, `:login`.

### `empty` Такого пользователя нет

`db → server` · `safe` · `with-defence`
Сообщение: 0 строк · Итог: ничего не найдено

#### Просто

База ищет пользователя с логином `admin' --` целиком, вместе с кавычкой и дефисами. Такого
пользователя нет.

#### По шагам

База сравнивает значения с логинами и паролями как обычный текст и возвращает пустой ответ.

#### Глубже

Значение `admin' --` сравнивается со столбцом `login` целиком, знак за знаком. Кавычка и `--`
здесь не код, а часть текста. Заменять параметры ручным экранированием кавычек OWASP настоятельно
не советует: легко ошибиться.

### `refuse` Отказ

`server → attacker` · `safe` · `with-defence`
Сообщение: Неверный вход · Итог: вход не выполнен

#### Просто

Сервер отвечает: неверный логин или пароль. Атака не удалась.

#### По шагам

Сервер возвращает обычную ошибку входа и ничего не рассказывает о своём устройстве.

#### Глубже

Если в базе случится ошибка, посетитель всё равно увидит только общее сообщение. Подробности
сервер записывает в свой журнал. Текст ошибки базы подсказал бы атакующему, как устроен запрос.

## Как защититься

- **Параметризованные запросы.** Сервер передаёт базе запрос и значения отдельно. Ввод посетителя
  остаётся данными, что бы в нём ни было. Это главная защита.
- **Белый список для частей запроса.** Имя таблицы или столбца и направление сортировки нельзя
  передать параметром. Сервер выбирает их только из своих заранее заданных вариантов.
- **Хранимые процедуры не спасают сами по себе.** Если внутри процедуры запрос снова склеивается
  из строк, инъекция возможна и там.
- **Не экранировать вручную.** Самодельная обработка кавычек — ненадёжная замена параметрам.
- **Минимальные права.** Учётная запись, от имени которой сайт ходит в базу, может только то,
  что нужно сайту. Это не останавливает инъекцию, но уменьшает ущерб.
- **Никаких ошибок базы наружу.** Посетитель видит общее сообщение, подробности остаются в
  журнале сервера.
