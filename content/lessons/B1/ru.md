## Шаги

### `form` Форма входа

`attacker → server` · `legit`
Сообщение: GET /login · Итог: страница входа

```http
POST /login
login=...&password=...
```

#### Просто

Атакующий открывает обычную страницу входа в интернет-магазин. Пока ничего плохого: так делает
любой посетитель.

#### По шагам

Браузер запрашивает страницу `/login`. Сервер отдаёт форму с полями «Логин» и «Пароль».

#### Глубже

Форма отправит запрос `POST /login` с параметрами `login` и `password`. Сервер подставит их в
SQL-запрос к таблице `users`.

### `trick` Хитрый логин

`attacker → server` · `attack`
Сообщение: admin' -- · Итог: принято как текст

```http
POST /login
login=⟦admin' --⟧&password=123
```

#### Просто

Вместо логина он вводит `admin` и приписывает кавычку с двумя дефисами. Для человека это мусор,
а для базы данных — **служебные знаки**.

#### По шагам

В поле «Логин» уходит строка `admin' --`, пароль любой. Сервер принимает её как обычный текст.

#### Глубже

Кавычка в SQL закрывает строку, а два дефиса начинают комментарий до конца строки. Сервер не
проверяет ввод и не отделяет его от кода запроса.

### `glue` Сервер склеивает запрос

`server → db` · `attack` · `without-defence`
Сообщение: SELECT ... · Итог: атака

```sql
SELECT * FROM users
WHERE login = '⟦admin' --⟧'
  AND password = '123'
```

#### Просто

Сервер берёт то, что ввёл посетитель, и **вклеивает прямо в вопрос к базе**. Кавычка обрывает
логин раньше времени, а дефисы вычёркивают проверку пароля.

#### По шагам

Сервер собирает запрос склейкой строк и отправляет базе. Часть про пароль превратилась в
комментарий.

#### Глубже

Ошибка в склейке строк: данные пользователя стали частью кода запроса. Третья строка запроса
теперь закомментирована.

### `answer` База отвечает

`db → server` · `attack` · `without-defence`
Сообщение: запись admin · Итог: найдена без пароля

#### Просто

База честно выполняет то, что ей прислали: найти пользователя admin. Про пароль её никто не
спросил.

#### По шагам

База возвращает запись пользователя admin. Отличить задуманный запрос от испорченного она не
может.

#### Глубже

После комментария запрос равен `SELECT * FROM users WHERE login = 'admin'`. Родственные приёмы:

- `' OR '1'='1` возвращает всех пользователей;
- `UNION SELECT` вытаскивает другие таблицы;
- слепая инъекция узнаёт данные по косвенным признакам ответа.

### `enter` Вход без пароля

`server → attacker` · `attack` · `without-defence`
Сообщение: Привет, admin · Итог: вход выполнен

#### Просто

Сервер видит, что база нашла пользователя, и пускает атакующего как администратора. Пароль он
так и не узнал: он не понадобился.

#### По шагам

Сервер создаёт сессию для admin и отдаёт личный кабинет.

#### Глубже

Итог — обход входа. Та же ошибка в других местах сайта позволяет читать и менять любые таблицы.
Класс ошибки CWE-89, в OWASP Top 10:2021 это пункт A03 «Инъекции».

### `param` Запрос с параметром

`server → db` · `attack` · `with-defence` · `stopped`
Сообщение: параметр: admin' -- · Итог: ввод остался данными, атака не сработала

```sql
SELECT * FROM users
WHERE login = ? AND password_hash = ?

параметр 1: ⟦admin' --⟧
```

#### Просто

Теперь сервер отправляет базе вопрос и ответ посетителя **отдельно**, как бланк и то, что в него
вписано. Вредный ввод `admin' --` доходит до базы, но только как вписанное значение: кавычка и
`--` в нём — просто буквы, команду они не меняют. Здесь атака и останавливается.

#### По шагам

Сервер отправляет шаблон запроса с местами для значений и отдельно сами значения. База
разбирает только шаблон, а значение сравнивает с логинами как обычный текст и не выполняет как
код.

#### Глубже

Это подготовленный запрос (*prepared statement*): структура запроса фиксируется до подстановки
данных, поэтому изменить её вводом нельзя.

### `empty` Такого пользователя нет

`db → server` · `safe` · `with-defence`
Сообщение: 0 строк · Итог: ничего не найдено

#### Просто

База ищет пользователя с дословным именем `admin' --` и, конечно, не находит.

#### По шагам

База возвращает пустой результат.

#### Глубже

Дополнительные слои: проверка ввода по белому списку и учётная запись базы с минимальными
правами. Ручное экранирование кавычек — ненадёжная замена параметрам.

### `refuse` Отказ

`server → attacker` · `safe` · `with-defence`
Сообщение: Неверный вход · Итог: вход не выполнен

#### Просто

Сервер отвечает: неверный логин или пароль. Атака не удалась.

#### По шагам

Сервер возвращает обычную ошибку входа, не раскрывая подробностей.

#### Глубже

Сообщение одинаково для неверного логина и неверного пароля, а текст ошибки базы наружу не
показывается: он подсказал бы атакующему устройство запроса.

## Как защититься

- **Параметризованные запросы.** Сервер передаёт базе шаблон запроса и значения отдельно; ввод
  посетителя остаётся данными, что бы в нём ни было.
- **Проверка ввода по белому списку** там, где значение не может быть параметром: имя столбца,
  направление сортировки.
- **Минимальные права.** Учётная запись, от имени которой сайт ходит в базу, может только то,
  что нужно сайту.
- **Никаких ошибок базы наружу.** Посетитель видит общее сообщение, подробности остаются в
  журнале сервера.
