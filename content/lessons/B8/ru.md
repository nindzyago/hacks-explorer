## Шаги

### `normal` Обычный вход

`attacker → server` · `legit`
Сообщение: login admin, пароль строкой · Итог: неверный пароль

```json
{"login": "admin", "password": "qwerty"}
```

#### Просто

Атакующий открывает страницу входа и пробует войти как `admin` с паролем наугад. Сайт отвечает:
неверный пароль. Но атакующий видит, **в каком виде** браузер отправляет логин и пароль: как
JSON.

#### По шагам

Форма входа шлёт на сервер маленький документ JSON с двумя полями. Сервер ищет в базе
пользователя, у которого совпадают и логин, и пароль.

#### Глубже

База здесь документная, вроде MongoDB: в ней не таблицы и не язык SQL, а документы, похожие на
JSON, и запросы, которые тоже записываются как объекты. Таких баз много, их зовут NoSQL.

### `swap` Пароль-условие

`attacker → server` · `attack`
Сообщение: password: {"$ne": ""} · Итог: принято как JSON

```json
{"login": "admin", "password": ⟦{"$ne": ""}⟧}
```

#### Просто

Теперь в поле пароля атакующий кладёт **не строку, а маленький объект**: `{"$ne": ""}`. Для базы
это условие «не равно пустой строке».

#### По шагам

JSON разрешает любое значение поля: строку, число, список или объект. Сервер разбирает такой JSON
без ошибок: формат правильный.

#### Глубже

Слова со знаком `$` в начале — операторы запроса MongoDB: `$ne` — «не равно», `$gt` —
«больше», `$regex` — «подходит под шаблон». В обычных данных они не нужны, а вот в запросе
меняют его смысл.

### `find` Запрос с условием

`server → db` · `attack` · `without-defence`
Сообщение: find: пароль не пустой · Итог: атака

```js
users.findOne({ login: "admin",
                password: ⟦{ $ne: "" }⟧ })
```

#### Просто

Сервер берёт поля из присланного JSON и **как есть** кладёт их в запрос. Вместо «пароль равен
qwerty» в запросе теперь «пароль не пустой».

#### По шагам

Код сервера писали, думая, что в поле придёт строка. Но язык не проверил тип, и объект
атакующего встал на место пароля целиком, вместе с оператором.

#### Глубже

Это ошибка CWE-943: запрос к хранилищу данных собирается так, что особые элементы во вводе меняют
его логику. OWASP подчёркивает: даже если запрос собран как объект, а не склейкой строк, это не
спасает, когда присланное значение само оказалось объектом.

### `match` Найден admin

`db → server` · `attack` · `without-defence`
Сообщение: документ admin · Итог: «пароль подошёл»

```text
login: "admin", password: ⟦любой непустой⟧ → найден
```

#### Просто

У администратора пароль, конечно, не пустой. Условие выполнено, и база **возвращает его
документ**, будто пароль верный.

#### По шагам

Сервер считает так: если база нашла пользователя с таким логином и паролем, значит, пароль
правильный. Проверка пароля целиком переложена на запрос, и запрос обманут.

#### Глубже

Для простоты сервер здесь сравнивает пароль прямо в запросе. На настоящем сайте в базе хранят хеш
пароля, но ошибка та же: оператор во вводе подменит условие в любом поле, по которому сервер ищет.

### `session` Вход как admin

`server → attacker` · `attack` · `without-defence`
Сообщение: cookie сессии admin · Итог: вход без пароля

```http
Set-Cookie: session=⟦сессия admin⟧
```

#### Просто

Сервер открывает сессию администратора. Атакующий **вошёл без пароля**.

#### По шагам

Дальше у атакующего всё, что может администратор: читать заметки всех пользователей, менять
настройки, удалять данные.

#### Глубже

Это аналог классической SQL-инъекции `' OR 1=1 --`, только без кавычек и комментариев: в запросе
нет ни одного «опасного» символа, которые обычно ищут фильтры. Подменён тип данных, а не текст.

### `type` Проверка типа

`server → server` · `attack` · `with-defence` · `stopped`
Сообщение: password не строка · Итог: отклонено, атака не сработала

```js
if (typeof password !== "string")
  → 400  // ⟦{"$ne": ""}⟧ — объект
```

#### Просто

В режиме защиты сервер сначала проверяет: **пароль — это строка?** Объект не строка, и запрос
отклоняется ещё до базы. Атака останавливается здесь.

#### По шагам

Каждое поле проверяется по своему правилу: логин — строка до 64 знаков, пароль — строка. Всё
остальное сервер не пропускает дальше, в базу ничего не уходит.

#### Глубже

Это совет OWASP: проверять ожидаемый простой тип значения до того, как строить фильтр, и не
передавать объекты от клиента как значения полей. Там же OWASP предупреждает, что проверка
«нет ли в JSON знака `$`» — это чёрный список, и он слабее проверки каждого поля.

### `deny` Отказ

`server → attacker` · `safe` · `with-defence`
Сообщение: 400 неверный запрос · Итог: атака не удалась

```http
HTTP/1.1 400 Bad Request
```

#### Просто

Атакующий получает отказ, как при любом неверном вводе. Вход не выполнен.

#### По шагам

Обычные пользователи этой проверки не замечают: их браузер и так присылает пароль строкой.

#### Глубже

Отказ стоит записать в журнал: объект в поле пароля — почти наверняка попытка атаки, а не
опечатка.

## Как защититься

- **Проверка типа каждого поля.** Логин и пароль — строки. Объект, список или число в таком поле —
  отказ.
- **Не передавать объекты клиента в запрос.** Значения в фильтр кладите только после проверки,
  а не весь присланный JSON целиком.
- **Запрет операторов от клиента.** Операторы вроде `$where`, `$regex`, `$expr` из присланных
  данных не принимайте, если без них можно обойтись.
- **Пароль проверяет код, а не запрос.** Найдите пользователя по логину, а пароль сверьте в коде
  хеш-функцией для паролей.
- **Без кода в запросах.** Не используйте `$where` с присланными строками и отключите выполнение
  JavaScript на сервере базы, если оно не нужно.
- **Меньше прав.** Учётная запись сайта в базе может только то, что сайту нужно.
