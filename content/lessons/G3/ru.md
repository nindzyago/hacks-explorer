## Шаги

### `type` Адрес без https

`user → attacker` · `legit` · `without-defence`
Сообщение: http://bank.example · Итог: первый запрос открытым текстом

```http
GET http://bank.example/
```

#### Просто

Посетитель набирает в браузере просто bank.example, без `https://`. Браузер начинает с обычного
HTTP. Атакующий уже стоит посередине, например так, как в уроке «Человек посередине», и получает
этот запрос первым.

#### По шагам

Обычно сайт отвечает на такой запрос перенаправлением на `https://`, и дальше всё зашифровано.
Атакующему нужно, чтобы это перенаправление до посетителя не дошло.

#### Глубже

Опасен именно первый шаг: запрос по HTTP никак не защищён. RFC 6797 называет эту слабость
уязвимостью первого визита (Bootstrap MITM Vulnerability, раздел 14.6): пока браузер не знает,
что сайт работает только по HTTPS, первый запрос можно перехватить.

### `upgrade` Атакующий говорит с банком по HTTPS

`attacker → bank` · `legit` · `without-defence`
Сообщение: HTTPS к банку · Итог: банк видит обычный защищённый вход

```text
к банку:     https://bank.example/  (TLS, всё как надо)
посетителю:  http://bank.example/   (без шифрования)
```

#### Просто

Атакующий сам идёт в банк **по HTTPS**, как обычный браузер. Для банка всё в порядке:
соединение зашифровано, сертификат настоящий. Просто на другом конце не посетитель, а атакующий.

#### По шагам

Атакующий держит два разговора: защищённый с банком и открытый с посетителем. Страницы банка он
пересылает посетителю, а запросы посетителя — банку.

#### Глубже

Подменять сертификат, как в уроке «Человек посередине», не нужно: с посетителем атакующий говорит
вообще без TLS, проверять браузеру нечего. Поэтому атака и называется «срезание SSL»: шифрование
не взламывают, его просто убирают с участка до жертвы.

### `strip` Ссылки без https

`attacker → user` · `attack` · `without-defence`
Сообщение: https → http · Итог: форма входа отправит пароль без шифрования

```html
<form action="⟦http⟧://bank.example/login" method="post">
```

#### Просто

Атакующий берёт страницу банка и **меняет все `https` на `http`**: в ссылках, в форме входа, в
перенаправлениях. Посетитель видит знакомую страницу. Нет только замочка в адресной строке, а это
мало кто замечает.

#### По шагам

Браузер не получил ни одного указания перейти на HTTPS, поэтому продолжает говорить по HTTP. С
точки зрения браузера ошибки нет: сайт просто открылся без шифрования.

#### Глубже

В MITRE ATT&CK такой переход с HTTPS на HTTP описан в технике T1689 «Downgrade Attack», в MITRE
CAPEC — в шаблоне CAPEC-620 «Drop Encryption Level». Родственная атака понижает не протокол, а
версию TLS: посредник срывает рукопожатие, и браузер, который пробует снова с более старой
версией, опускается до слабой. На таком откате до SSL 3.0 строилась атака POODLE
(CVE-2014-3566, 2014 год).

### `login` Пароль открытым текстом

`user → attacker` · `attack` · `without-defence`
Сообщение: пароль по HTTP · Итог: пароль у атакующего, вход выполнен

```http
POST http://bank.example/login
login=anna&password=⟦Kot2024⟧
```

#### Просто

Посетитель вводит логин и пароль. Форма уходит по HTTP, и атакующий **читает пароль**. Потом он
пересылает форму в банк по HTTPS, и вход проходит как обычно.

#### По шагам

Банк видит защищённое соединение и правильный пароль. Посетитель видит свой кабинет. Пароль и
куки сессии уже у атакующего.

#### Глубже

Передача пароля без шифрования — CWE-319 «Передача важных данных открытым текстом», в OWASP
Top 10:2021 это пункт A02 «Криптографические сбои». Банк может даже не узнать об атаке: со своей
стороны он видит только HTTPS.

### `preload` Браузер сразу выбирает HTTPS

`user → attacker` · `safe` · `with-defence`
Сообщение: сразу https · Итог: банк в списке предзагрузки HSTS

```text
bank.example в списке предзагрузки HSTS → сразу https://bank.example/
```

#### Просто

Теперь банк включил **HSTS** и попал в список предзагрузки, встроенный в браузеры. Посетитель
снова набирает просто bank.example, но браузер сам меняет адрес на `https://` ещё до отправки.

#### По шагам

Открытого запроса по HTTP больше нет. Браузер начинает рукопожатие TLS и ждёт от банка сертификат
на bank.example.

#### Глубже

По RFC 6797 браузер, который знает, что сайт работает только по HTTPS, сам переписывает любые
ссылки `http://` на `https://` и не даёт пройти мимо ошибки сертификата. Список предзагрузки
закрывает первый визит. По MDN, чтобы попасть в список, сайт присылает
`Strict-Transport-Security` с `max-age` не меньше года (31536000 секунд), `includeSubDomains` и
`preload`.

### `redirect` Попытка вернуть http

`attacker → user` · `attack` · `with-defence` · `stopped`
Сообщение: иди на http · Итог: браузер сам вернул https, подмена не прошла

```http
HTTP/1.1 302 Found
Location: ⟦http⟧://bank.example/login
```

#### Просто

Атакующий пробует отправить браузер обратно на `http`. Но браузер помнит правило HSTS для
bank.example и **сам меняет `http` на `https`**. Срезать шифрование не удалось, здесь атака и
останавливается.

#### По шагам

Подменить сертификат атакующий тоже не может: настоящего у него нет, а мимо ошибки сертификата
HSTS пройти не даст. Остаётся только пересылать зашифрованные пакеты, не читая их.

#### Глубже

HSTS защищает и поддомены, если в заголовке есть `includeSubDomains`. Без этого атакующий может
заманить браузер на какой-нибудь поддомен банка по HTTP, и куки, которые сайт ставит на весь
домен, остаются под угрозой (RFC 6797, раздел 14.4).

### `old` Попытка понизить версию

`attacker → bank` · `attack` · `with-defence` · `stopped`
Сообщение: только TLS 1.0 · Итог: банк отказал: старые версии выключены

```text
поддерживаю: ⟦TLS 1.0⟧
ответ банка: протокол не поддерживается, соединение закрыто
```

#### Просто

Атакующий пробует другой путь: сорвать рукопожатие, чтобы браузер и банк договорились о
**старой, слабой версии** TLS. Но банк просто не умеет говорить на старых версиях: он их
выключил. Рукопожатие не состоится.

#### По шагам

Банк принимает только TLS 1.2 и TLS 1.3. По тем же правилам и браузер не должен предлагать
старые версии. Понижать некуда.

#### Глубже

RFC 7568 (2015) запретил SSL 3.0, RFC 8996 (2021) — TLS 1.0 и 1.1: их нельзя использовать и о них
нельзя договариваться. В TLS 1.3 есть своя защита (RFC 8446, раздел 4.1.3): сервер, который
согласился на версию ниже, оставляет в своём случайном числе особую метку, и браузер, видя её,
прерывает соединение. Раньше от понижения при повторных попытках защищал отдельный сигнал
TLS_FALLBACK_SCSV (RFC 7507); когда старые версии запретили, RFC 8996 объявил его устаревшим.

### `secure` Защищённый вход

`user → bank` · `safe` · `with-defence`
Сообщение: TLS 1.3 · Итог: пароль зашифрован

#### Просто

Браузер и банк договорились о **TLS 1.3** и проверили сертификат. Пакеты по-прежнему идут через
атакующего, но он видит только шифр.

#### По шагам

Посетитель вводит пароль, и он уходит внутри зашифрованного соединения. Подменить ссылки или
форму атакующий не может: любое изменение браузер заметит.

#### Глубже

Защита работает, потому что решение «только HTTPS» принимает браузер, а не страница, которую
может подменить посредник. HSTS и список предзагрузки переносят это решение туда, куда атакующий
не дотягивается.

## Как защититься

- **HTTPS на всём сайте и перенаправление с HTTP.** Ни одной страницы, формы или картинки по
  `http://`.
- **HSTS с долгим сроком.** Заголовок `Strict-Transport-Security` с `max-age` не меньше года и
  `includeSubDomains`: браузер сам ходит только по HTTPS и не даёт пройти мимо ошибки
  сертификата.
- **Список предзагрузки HSTS.** Добавьте домен в список, встроенный в браузеры: тогда защищён и
  самый первый визит.
- **Только TLS 1.2 и 1.3.** Выключите SSL 3.0, TLS 1.0 и TLS 1.1 на серверах (RFC 7568, RFC 8996).
- **Куки с пометкой `Secure`.** Такие куки браузер не отправит по HTTP, даже если атакующий
  заманит его туда.
- **Посетителю: смотрите на замочек.** Если сайт банка вдруг открылся без HTTPS, особенно в
  общей сети, не вводите пароль.
