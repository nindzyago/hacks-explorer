## Шаги

### `trust` Годы помощи проекту

`attacker → maint` · `attack`
Сообщение: помощь и патчи · Итог: доступ к коду получен

#### Просто

**xz** — маленькая программа и библиотека сжатия, которая входит во многие дистрибутивы Linux.
Ведёт проект один человек. Появляется участник, который помогает: присылает исправления,
участвует в обсуждениях. Со временем ему **начинают доверять**.

#### По шагам

Сопровождающий устал, а тут кто-то берёт часть работы на себя. Новый участник получает право
вносить изменения прямо в код проекта.

#### Глубже

CISA называет это многолетними усилиями злоумышленника, чтобы войти в доверие к сопровождающему
пакета. В этой истории CISA видит и хрупкость открытой экосистемы: груз безопасности лёг на
одного сопровождающего, уставшего от работы. В ATT&CK такой путь — T1195.001, компрометация
зависимостей и инструментов разработки.

### `tests` «Тестовые» файлы

`attacker → maint` · `attack`
Сообщение: тестовые файлы · Итог: в репозитории

```text
tests/files/⟦bad-3-corrupt_lzma2.xz⟧
tests/files/⟦good-large_compressed.lzma⟧
```

#### Просто

Участник добавляет в проект пару файлов будто бы **для тестов**: испорченные архивы, на которых
проверяют, как библиотека справляется с ошибками. В таких файлах никто не ищет код.

#### По шагам

Внутри файлов — запутанная часть закладки. Сами по себе они ничего не делают:
просто лежат среди сотен других тестовых данных.

#### Глубже

По сообщению на oss-security, основная часть закладки лежала в этих двух файлах в запутанном
виде, и в версии 5.6.0 они даже не использовались ни одним тестом. NVD: процесс сборки liblzma
извлекает готовый объектный файл из замаскированного тестового файла и с его помощью меняет
функции библиотеки. Вредный код, встроенный в программу, — CWE-506.

### `release` Архив выпуска с лишней строкой

`attacker → build` · `attack` · `without-defence`
Сообщение: архив · Итог: принят как обычный выпуск

```text
m4/build-to-host.m4:  ⟦строка, которой нет в git⟧
```

#### Просто

Выходит новая версия xz. Дистрибутивы Linux берут для сборки **архив выпуска**. В нём есть одна
лишняя строка, которой нет в открытом репозитории проекта. Её никто не сверяет.

#### По шагам

Архив выпуска обычно собирают из репозитория и добавляют служебные файлы для сборки. Хакер
спрятал запуск закладки именно в таком служебном файле: в коде на сайте проекта его не видно.

#### Глубже

По oss-security, строка в `build-to-host.m4` была только в архивах 5.6.0 и 5.6.1 и не было её ни
в исходном build-to-host, ни в git проекта. Архивы «исходный код», которые, по словам нашедшего,
сайт хранения кода собирает прямо из репозитория, этой строки не содержали. Строка запускает в конце `configure` запутанный
скрипт.

### `checked` Архив сверяют с репозиторием

`attacker → build` · `attack` · `with-defence` · `stopped`
Сообщение: архив · Итог: архив не совпал с git, атака не сработала

```text
diff архив ↔ git-тег v5.6.0:  ⟦m4/build-to-host.m4⟧ есть только в архиве
```

#### Просто

Сборщики дистрибутива **сверяют** архив выпуска с тем же тегом в репозитории. Служебного файла с лишней строкой в репозитории нет, поэтому архив не берут: пакет собирают прямо из репозитория, а служебные файлы создают сами.

#### По шагам

Без строки в служебном файле запутанные «тестовые» файлы никто не распаковывает. Закладка
остаётся мёртвым грузом в папке тестов.

#### Глубже

Сверка архива с репозиторием не спасает от закладки, которую внесли в сам репозиторий, но заставляет её быть на виду, где код читают люди. Здесь запуск был спрятан
именно там, куда никто не смотрел.

### `compile` Сборка с закладкой

`build → build` · `attack` · `without-defence`
Сообщение: configure и make · Итог: liblzma с закладкой

```text
if x86-64 Linux, gcc и GNU ld, сборка пакета deb или RPM:
    ⟦достать код из тестового файла и встроить в liblzma⟧
```

#### Просто

Сервер сборки собирает пакет как обычно. Скрипт из лишней строки **достаёт код** из
«тестового» файла и подмешивает его в библиотеку. Получается liblzma с закладкой.

#### По шагам

Скрипт срабатывает не везде, а только при сборке пакета дистрибутива на нужной машине. На
компьютере программиста, который собирает xz для проверки, всё выглядит чисто.

#### Глубже

По разбору на oss-security, скрипт проверял, что сборка идёт для x86-64 Linux, компилятором gcc с
компоновщиком GNU ld и внутри сборки пакета deb или RPM. Последнее, вероятно, должно было
затруднить расследование. Работать закладка, судя по устройству, могла только в системах с glibc.

### `install` Пакет приходит на сервер

`build → server` · `attack` · `without-defence`
Сообщение: пакет xz · Итог: sshd грузит закладку

#### Просто

Сервер ставит обновление. Служба входа по **SSH** сама xz не использует, но в некоторых
дистрибутивах она подключает другую библиотеку, а та — liblzma. Так закладка оказывается внутри
службы входа.

#### По шагам

При запуске `sshd` закладка подменяет в нём функцию, которая проверяет ключ RSA при входе. Теперь
каждая попытка входа по ключу проходит через код хакера.

#### Глубже

По oss-security: Debian и ряд других дистрибутивов дорабатывают OpenSSH для уведомлений systemd,
а libsystemd зависит от lzma. Закладка перенаправляла `RSA_public_decrypt` в своём коде. К счастью,
5.6.0 и 5.6.1 почти не успели попасть в дистрибутивы, а где попали — в основном в тестовые
версии. CISA советовала откатиться на чистую версию, например XZ Utils 5.4.6.

### `backdoor` Вход в обход проверки

`attacker → server` · `attack` · `without-defence`
Сообщение: вход по SSH · Итог: проверка ключа перехвачена

#### Просто

Хакер подключается к серверу по SSH. Закладка видит его попытку **раньше настоящей проверки** и
может пропустить его — на сервере, который об этом не знает.

#### По шагам

Это до входа, без пароля и без действий человека. Поэтому NVD оценивает уязвимость в 10.0 из 10:
`S:C` значит, что ущерб выходит за пределы самой библиотеки сжатия.

#### Глубже

Нашедший закладку разработчик написал, что код работает до проверки подлинности и, вероятно,
даёт какой-то доступ или выполнение кода. Заметил он её по побочному эффекту: вход по SSH на
тестовой системе стал заметно медленнее — около 0,8 с вместо 0,3 с, а запуск `sshd -h` занимал
около 0,5 с вместо 0,01 с. 29 марта 2024 года он сообщил об этом на oss-security, и в тот же день
CISA выпустила предупреждение.

### `gitbuild` Чистый пакет из репозитория

`build → server` · `safe` · `with-defence`
Сообщение: пакет xz · Итог: чистая библиотека

#### Просто

Пакет собран из проверенного кода, без лишней строки. Сервер получает **обычную** библиотеку
сжатия.

#### По шагам

`sshd` запускается и проверяет ключи сам, как и задумано. Чужого кода в процессе нет.

#### Глубже

Чистый пакет ещё и не тормозит вход: никакой лишней работы при запуске `sshd`. Именно разница во
времени выдала закладку в реальной истории.

### `login` Обычная проверка ключа

`attacker → server` · `attack` · `with-defence` · `stopped`
Сообщение: вход по SSH · Итог: ключ не подошёл, атака не сработала

#### Просто

Хакер пробует войти, но его ключа нет в списке разрешённых. `sshd` **отказывает**, как любому
чужому.

#### По шагам

Попытка остаётся в журнале сервера. Ни команд, ни доступа хакер не получил.

#### Глубже

Второй рубеж для таких серверов — не пускать к SSH кого попало: вход только из нужных сетей или
через отдельный шлюз. Тогда даже закладка в службе входа была бы недоступна из интернета.

## Как защититься

- **Сверять архив выпуска с репозиторием.** Собирать пакеты из проверенного тега или проверять,
  что в архиве нет кода, которого нет в репозитории.
- **Воспроизводимая сборка.** Одинаковый результат на разных машинах выдаёт подмену в процессе сборки. Но архив с закладкой соберётся одинаково везде — его нужно сверять с репозиторием.
- **Поддерживать сопровождающих.** CISA призывает компании, которые зарабатывают на открытом коде,
  вкладываться в проекты деньгами или временем разработчиков, чтобы проект не держался на одном
  уставшем человеке.
- **Быстро откатываться.** Знать, где стоит библиотека (SBOM), и уметь быстро вернуть проверенную
  версию, как советовала CISA.
- **Не открывать SSH всему интернету.** Ограничить вход по сетям или через шлюз.
- **Замечать странности.** Закладку выдали лишние полсекунды при входе и странные ошибки valgrind:
  необычное поведение стоит разбирать, а не списывать на случайность.
