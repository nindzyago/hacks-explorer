## Шаги

### `assign` Ольга выдаёт роль

`admin → server` · `legit`
Сообщение: роль для № 42 · Итог: роль выдана

```http
POST /admin/users/42/role
Cookie: session=…ольга…

role=editor
```

#### Просто

Ольга — администратор интернет-магазина. В своей панели она нажимает кнопку и делает сотрудника
с номером 42 **редактором** каталога.

#### По шагам

Кнопка в панели отправляет запрос на служебный адрес `/admin/users/42/role` вместе с cookie
сессии Ольги. Сервер меняет роль в таблице `users`.

#### Глубже

У каждого пользователя есть **роль**: покупатель, редактор, администратор. Роль решает, что
человеку можно. Обычные покупатели этой кнопки не видят: сайт рисует её только администраторам.
Но спрятать кнопку — ещё не значит закрыть адрес, на который она ведёт.

### `peek` Атакующий находит адрес

`attacker → server` · `legit`
Сообщение: GET /app.js · Итог: адрес найден

```javascript
// в коде страницы, который получают все
fetch(`⟦/admin/users/${id}/role⟧`, …)
```

#### Просто

Атакующий — обычный покупатель со своим аккаунтом. Он открывает код страницы, который браузер
и так скачивает, и находит в нём **служебный адрес** для смены роли.

#### По шагам

Скрипт сайта общий для всех: в нём лежат и функции админ-панели, просто у покупателя они не
показываются. Адрес можно найти и перебором: `/admin`, `/manage`, `/internal`.

#### Глубже

Скрытый интерфейс — защита только для глаз. Всё, что получил браузер, атакующий может прочитать,
а любой запрос — отправить сам, без кнопки. OWASP прямо говорит: проверки на стороне клиента
улучшают удобство, но решать, кому что можно, должен сервер.

### `promote` Запрос себе в админы

`attacker → server` · `attack` · `without-defence`
Сообщение: № 77 → admin · Итог: принято

```http
POST /admin/users/77/role
Cookie: session=…атакующий…

role=⟦admin⟧
```

#### Просто

Атакующий сам отправляет тот же запрос, что и кнопка Ольги, но для **своего** номера 77 и с ролью
**admin**.

#### По шагам

Сессия у запроса — атакующего, он вошёл честно. Сервер проверяет только одно: вошёл ли
посетитель. Проверки «а администратор ли он» на этом адресе нет.

#### Глубже

Это **вертикальное** повышение привилегий: пользователь получает права более высокого уровня.
Горизонтальное — доступ к данным соседа с той же ролью, как в уроке про IDOR. В каталоге MITRE
ошибка здесь — CWE-862 «Missing Authorization»: сервер не делает проверку прав, когда кто-то
вызывает действие.

### `guard` Сервер проверяет роль

`attacker → server` · `attack` · `with-defence` · `stopped`
Сообщение: № 77 → admin · Итог: атака не сработала

```http
POST /admin/users/77/role
Cookie: session=…атакующий…

role=⟦admin⟧
```

#### Просто

Тот же запрос, но теперь сервер на каждом служебном адресе спрашивает: **какая роль** у того, кто
пришёл? У атакующего роль «покупатель», и сервер его останавливает.

#### По шагам

Роль сервер берёт из своей записи о сессии, а не из запроса. Правило для адресов `/admin/…` одно
на весь сайт: пускать только роль `admin`, всех остальных — нет.

#### Глубже

Так работает принцип «запрещено по умолчанию»: если нет правила, которое явно разрешает, ответ —
отказ. OWASP советует проверять права на каждом запросе и в одном общем месте: атакующему
достаточно найти один забытый адрес.

### `write` Роль записана

`server → db` · `attack` · `without-defence`
Сообщение: role = admin для 77 · Итог: атака

```sql
UPDATE users SET role = ⟦'admin'⟧
WHERE id = 77
```

#### Просто

Сервер послушно записывает в базу: пользователь 77 теперь **администратор**.

#### По шагам

Запрос к базе составлен правильно, инъекции нет. Ошибка не в базе, а раньше: сервер не спросил,
можно ли этому человеку менять роли.

#### Глубже

CWE-269 «Improper Privilege Management» описывает шире: система неправильно выдаёт, меняет,
отслеживает или проверяет права, и у кого-то появляется власть, которой не задумывали. Здесь
право «менять роли» фактически есть у любого вошедшего.

### `owned` Атакующий — администратор

`server → attacker` · `attack` · `without-defence`
Сообщение: 200 OK, роль admin · Итог: права захвачены

```http
HTTP/1.1 200 OK
```

#### Просто

Атакующий обновляет страницу и видит **админ-панель**: все заказы, все покупатели, цены, скидки.

#### По шагам

С ролью администратора он может выдавать роли другим, менять товары и читать данные всех
клиентов. Со стороны это выглядит как обычная работа администратора.

#### Глубже

В OWASP Top 10:2021 это пункт A01 «Broken Access Control». Среди его примеров — работа под
администратором, войдя обычным пользователем, и вызов API, где у POST, PUT и DELETE нет
проверки доступа.

### `deny` Отказ: нет прав

`server → attacker` · `safe` · `with-defence`
Сообщение: 403 Forbidden · Итог: роль не изменилась

```http
HTTP/1.1 403 Forbidden
```

#### Просто

Сервер отвечает: **нельзя**. Роль атакующего осталась прежней, в базу ничего не записано.

#### По шагам

Ответ 403 по стандарту HTTP значит: сервер понял запрос, но выполнять его отказывается. Отказ
записывается в журнал.

#### Глубже

RFC 9110 (раздел 15.5.4) разрешает вместо 403 ответить 404, если сервер не хочет показывать, что
такой адрес вообще есть. Журнал отказов полезен: попытки обычного пользователя вызвать служебные
адреса — явный признак атаки.

## Как защититься

- **Проверка прав на сервере, на каждом запросе.** Каждый служебный адрес сам проверяет роль
  того, кто пришёл. Скрытая кнопка или скрытый адрес ничего не защищают.
- **Запрещено по умолчанию.** Новый адрес закрыт, пока для него нет правила, которое явно
  разрешает доступ.
- **Одна общая проверка.** Правила доступа описаны в одном месте и действуют для всех адресов,
  а не пишутся заново в каждом.
- **Роль — из сессии сервера.** Кто пришёл и какая у него роль, сервер берёт из своих данных, а
  не из полей запроса.
- **Минимум прав.** Каждой роли — только то, что нужно для работы; права время от времени
  пересматриваются.
- **Тесты и журнал.** Автотесты входят обычным пользователем и вызывают служебные адреса — ответ
  должен быть отказом. Отказы пишутся в журнал, частые отказы поднимают тревогу.
