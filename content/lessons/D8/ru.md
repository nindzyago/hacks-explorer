## Шаги

### `avatar` Аватар по ссылке

`attacker → server` · `legit`
Сообщение: ссылка на картинку · Итог: принято

```http
POST /avatar
Host: shop.example

url=https://pics.example/cat.png
```

#### Просто

В магазине можно поставить аватар **по ссылке**: вставить адрес картинки, и сайт сам её скачает.
Атакующий сначала пробует обычную картинку.

#### По шагам

Ссылку принимает сервер магазина. Скачивать картинку будет **он**, а не браузер посетителя.

#### Глубже

Такие функции встречаются часто: предпросмотр ссылок в чате, импорт файла по адресу, проверка
вебхука, конвертер страниц в PDF. Во всех них сервер делает запрос по адресу, который выбрал
посетитель.

### `fetch` Сервер скачивает картинку

`server → pics` · `legit`
Сообщение: GET /cat.png · Итог: картинка получена

```http
GET /cat.png
Host: pics.example
```

#### Просто

Сервер идёт на фотосайт, скачивает картинку и показывает её атакующему как новый аватар. Всё
как задумано.

#### По шагам

Атакующий убедился: сервер **сам ходит** по присланной ссылке и возвращает то, что получил.

#### Глубже

Важно, откуда идёт запрос. Его отправляет машина внутри облака магазина, а ей доступны адреса,
до которых из интернета не достать: внутренние службы, базы, панели управления.

### `evil-url` Ссылка внутрь

`attacker → server` · `attack` · `without-defence`
Сообщение: ссылка на метаданные · Итог: принято

```http
POST /avatar

url=⟦http://192.0.2.254/secrets/role-key⟧
```

#### Просто

Теперь атакующий присылает ссылку не на картинку, а на **внутреннюю службу облака**. Из интернета
её не открыть, а сервер магазина видит её рядом с собой.

#### По шагам

Сервер не проверяет адрес: ссылка как ссылка. Он готовится скачать «картинку» по этому адресу.

#### Глубже

У виртуальных машин в облаке есть **служба метаданных**: она отвечает самой машине, что это за
машина, и выдаёт ей временные ключи доступа к облаку. В настоящих облаках у неё особый служебный
адрес из диапазона link-local, одинаковый у многих провайдеров; в уроке вместо него учебный
192.0.2.254, а путь выдуман.

### `inside` Запрос к метаданным

`server → meta` · `attack` · `without-defence`
Сообщение: запрос ключей · Итог: ключи выданы

```http
GET /secrets/role-key
Host: 192.0.2.254
```

#### Просто

Служба метаданных получает запрос **от своей же машины** и спокойно отвечает. Она не знает, что
адрес подсказал атакующий.

#### По шагам

В ответе — временные ключи, с которыми сервер магазина работает с облаком: хранилище файлов,
очереди, базы.

#### Глубже

MITRE ATT&CK описывает это как подтехнику T1552.005 «Cloud Instance Metadata API» и прямо
называет одним из путей к ней SSRF в веб-прокси, доступном из интернета; наш сервер с
аватарами по ссылке работает как такой прокси. OWASP отмечает: в облаке SSRF
часто используют, чтобы украсть ключи и токены из службы метаданных.

### `keys` Ключи у атакующего

`server → attacker` · `attack` · `without-defence`
Сообщение: «аватар» с ключами · Итог: ключи у атакующего

```json
{"key": "⟦AKEXAMPLE…⟧", "secret": "⟦…⟧", "expires": "…"}
```

#### Просто

Сервер отдаёт атакующему то, что «скачал», — **ключи облака** вместо картинки. С ними атакующий
обращается к облаку магазина напрямую.

#### По шагам

Сервер не проверил, что пришла картинка, и вернул ответ как есть. Даже без этого атакующий
иногда узнаёт ответ по косвенным признакам: по ошибке, по времени, по размеру.

#### Глубже

В каталоге MITRE эта слабость — CWE-918: сервер получает адрес и скачивает его содержимое, не
убедившись, что запрос идёт туда, куда задумано. OWASP вынес её в отдельный пункт A10:2021 по
итогам опроса сообщества: случаев немного, но последствия тяжёлые, особенно в облаке.

### `allowlist` Проверка адреса до запроса

`attacker → server` · `attack` · `with-defence` · `stopped`
Сообщение: ссылка на метаданные · Итог: атака не сработала

```text
адрес:   ⟦192.0.2.254⟧
список:  pics.example, img.example
итог:    не в списке → отказ
```

#### Просто

Сервер скачивает картинки **только с разрешённых сайтов** — по белому списку. Внутреннего адреса
в нём нет, и запрос не отправляется.

#### По шагам

Сервер разбирает ссылку сам: схема только `https`, хост из списка, порт стандартный. Затем
узнаёт IP-адрес хоста и проверяет, что он не внутренний, и подключается **именно к проверенному**
адресу.

#### Глубже

OWASP советует белый список, а не чёрный: запрет внутренних адресов обходят другой записью того
же адреса (десятичной, шестнадцатеричной, через IPv6) или доменом, который указывает внутрь.
Проверка имени без проверки адреса не спасает от DNS rebinding: при втором запросе DNS тот же
домен указывает уже на внутренний адрес. Ещё нужно выключить переходы по перенаправлениям, иначе
разрешённый сайт ответит «иди по внутреннему адресу».

### `refuse` Отказ вместо скачивания

`server → attacker` · `safe` · `with-defence`
Сообщение: 400 · Итог: ключи на месте

```http
HTTP/1.1 400 Bad Request

ссылка не разрешена
```

#### Просто

Атакующий получает **отказ**. Служба метаданных запроса так и не увидела.

#### По шагам

Попытка записывается в журнал: ссылка на внутренний адрес в форме аватара — явный признак
атаки.

#### Глубже

Защиту ставят и на уровне сети: машине, которая скачивает чужие ссылки, по правилу «запрещено
всё, что не разрешено» закрывают дорогу во внутреннюю сеть. Для облака AWS OWASP советует
перейти на IMDSv2 и выключить старую версию IMDSv1 — это дополнительная защита службы
метаданных от части атак SSRF.

## Как защититься

- **Белый список.** Сервер ходит только на заранее разрешённые хосты, схемы и порты и сам
  собирает адрес запроса.
- **Проверка IP-адреса.** После DNS сервер проверяет итоговый адрес и подключается именно к нему;
  внутренние, локальные и link-local адреса запрещены.
- **Без перенаправлений.** Клиент сервера не идёт по ответу «иди по другому адресу».
- **Не отдавать ответ как есть.** Пользователь получает картинку после проверки, а не сырой ответ
  чужого сервера.
- **Сеть.** Функцию скачивания ставят в отдельный сегмент сети, исходящие соединения — по правилу
  «запрещено всё, что не разрешено».
- **Служба метаданных.** Включают её защищённый режим (в AWS — IMDSv2) и дают машине ключи с
  минимальными правами.
