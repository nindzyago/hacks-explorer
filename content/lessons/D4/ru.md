## Шаги

### `login` Обычный вход

`attacker → server` · `legit`
Сообщение: логин и пароль · Итог: пароль верный

```http
POST /login

login=boris&password=…
```

#### Просто

Атакующий — обычный пользователь сервиса. Он входит под своим логином и паролем, как все.

#### По шагам

Сервер проверяет пароль. Вместо номера сессии он выдаст **токен** — пропуск, который клиент будет
показывать с каждым запросом.

#### Глубже

Токен удобен тем, что серверу не нужно хранить сессии: всё нужное записано в самом токене. Но
тогда сервер должен быть уверен, что токен написал он сам, а не кто-то другой.

### `token` Сервер выдаёт JWT

`server → attacker` · `legit`
Сообщение: JWT, role user · Итог: токен выдан

```text
{"alg":"HS256","typ":"JWT"}
{"sub":"77","role":"user","exp":…}
подпись: HMAC(секрет сервера)
```

#### Просто

Сервер выдаёт **JWT** из трёх частей: заголовок, данные и подпись. В данных написано: пользователь
77, роль `user`. Подпись ставит сервер своим секретом.

#### По шагам

Части кодируются в base64url и склеиваются через точки. Это кодирование, а не шифрование: любой
может раскодировать токен и прочитать, что в нём. Защищает его только подпись.

#### Глубже

Формат описан в RFC 7519. Заголовок `alg` говорит, каким алгоритмом подписан токен: здесь HS256,
то есть HMAC с SHA-256 и общим секретом. Поле `exp` — срок годности токена. OWASP напоминает, что
подписанный JWT не секретен: паролей и личных данных в нём быть не должно.

### `forge` Атакующий переписывает токен

`attacker → attacker` · `attack`
Сообщение: alg none, role admin · Итог: подделка готова

```text
{"alg":"⟦none⟧","typ":"JWT"}
{"sub":"77","role":"⟦admin⟧","exp":…}
подпись: ⟦(пусто)⟧
```

#### Просто

Атакующий меняет в данных роль на **admin**. Подписать его он не может — секрета нет. Поэтому он
пишет в заголовке: «алгоритм — **none**», то есть «подписи нет», и подпись просто убирает.

#### По шагам

Всё делается у атакующего, без обращения к серверу: раскодировать, поменять два поля,
закодировать обратно. Вопрос лишь в том, поверит ли сервер.

#### Глубже

Значение `none` в стандарте есть: RFC 7518 (раздел 3.6) описывает токен без подписи. Но там же
сказано, что реализации **не должны** принимать такие токены по умолчанию. RFC 8725 описывает
ещё одну атаку на `alg`: токен с RS256 переписывают на HS256, и библиотека проверяет HMAC, взяв
открытый ключ RSA как секрет.

### `accept` Сервер верит заголовку

`attacker → server` · `attack` · `without-defence`
Сообщение: Bearer с alg none · Итог: принято

```http
GET /admin/users
Authorization: Bearer ⟦eyJhbGciOiJub25lIi…⟧
```

#### Просто

Сервер читает заголовок токена, видит «подписи нет» и **верит** ему: проверять нечего. В данных
написано `admin` — значит, админ.

#### По шагам

Сервер передаёт токен библиотеке и спрашивает «токен верный?». Библиотека берёт алгоритм из
самого токена, а не из настроек сервера. Алгоритм `none` проверку проходит всегда.

#### Глубже

В каталоге MITRE это CWE-347 «Improper Verification of Cryptographic Signature»: подпись не
проверяется или проверяется неправильно. Корень ошибки — решение о проверке принимает тот, кого
проверяют: алгоритм выбирает присланный токен.

### `verify` Подпись проверяется строго

`attacker → server` · `attack` · `with-defence` · `stopped`
Сообщение: Bearer с alg none · Итог: атака не сработала

```http
GET /admin/users
Authorization: Bearer ⟦eyJhbGciOiJub25lIi…⟧
```

#### Просто

Теперь сервер сам знает, каким алгоритмом подписывает свои токены, — **только HS256**. Токен с
`none` он отвергает сразу, до чтения роли.

#### По шагам

Список разрешённых алгоритмов задан в настройках сервера. Токен с другим алгоритмом, без подписи
или с неверной подписью не принимается. Роль из токена читается только после проверки.

#### Глубже

RFC 8725 (раздел 3.1) требует, чтобы библиотека давала задать разрешённые алгоритмы и не
использовала никакие другие, а каждый ключ подходил ровно к одному алгоритму. Это закрывает и
`none`, и подмену RS256 на HS256.

### `dump` Запрос от имени админа

`server → db` · `attack` · `without-defence`
Сообщение: все пользователи · Итог: атака

```sql
SELECT * FROM users
```

#### Просто

Сервер считает атакующего администратором и выгружает из базы **всех пользователей**.

#### По шагам

Проверка роли на сервере есть, но она смотрит в токен, а токен написал сам атакующий. Проверка
прав работает правильно — на ложных данных.

#### Глубже

В OWASP Top 10:2021 подмена или повтор JWT названы среди примеров пункта A01 «Broken Access
Control». CWE-347 OWASP относит к A02 «Cryptographic Failures».

### `leak` Данные утекли

`server → attacker` · `attack` · `without-defence`
Сообщение: список пользователей · Итог: права захвачены

```http
HTTP/1.1 200 OK
```

#### Просто

Атакующий получает **админ-доступ** без пароля администратора — одним самодельным токеном.

#### По шагам

Тот же приём работает для любого пользователя: достаточно вписать в токен чужой номер `sub`.

#### Глубже

Есть и другой путь к подделке — **слабый секрет**. Если HS256 подписан коротким или словарным
паролем, атакующий с одним настоящим токеном подбирает секрет у себя, без запросов к серверу
(RFC 8725, раздел 2.2), и дальше подписывает что угодно.

### `reject` Отказ: токен не принят

`server → attacker` · `safe` · `with-defence`
Сообщение: 401 Unauthorized · Итог: доступа нет

```http
HTTP/1.1 401 Unauthorized
```

#### Просто

Сервер отвечает: **токен недействителен**. Список пользователей атакующий не получил.

#### По шагам

Отказ записывается в журнал. Токен без подписи от клиента — явный признак атаки.

#### Глубже

Строгая проверка подписи нужна вместе с другими: секрет HS256 не короче 256 бит (RFC 7518,
раздел 3.2), случайный, а не пароль (RFC 8725, раздел 3.5), короткий срок `exp`, проверка `iss` и
`aud`. Отозвать выданный JWT
трудно, поэтому OWASP советует держать срок жизни коротким.

## Как защититься

- **Проверять подпись всегда и самим выбирать алгоритм.** Сервер задаёт список разрешённых
  алгоритмов в своих настройках; `alg` из токена не решает ничего. `none` не принимается.
- **Один ключ — один алгоритм.** Ключ для RS256 не используется как секрет HMAC; так закрыта
  путаница алгоритмов.
- **Сильный секрет.** Для HS256 — случайный секрет не короче 256 бит из криптографического
  генератора, не пароль.
- **Короткий срок жизни.** Поле `exp` проверяется; токены живут недолго, а для отзыва есть
  список отозванных.
- **Проверять, кто выдал и для кого.** Поля `iss` и `aud` сверяются с ожидаемыми.
- **Ничего секретного внутри.** JWT читается любым, кто его получил: только подпись защищает его
  от изменения, а не от чтения.
