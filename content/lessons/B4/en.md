## Steps

### `avatar` A new avatar

`attacker → server` · `legit`
Message: me.png · Result: accepted

```http
POST /avatar
filename="me.png"
Content-Type: image/png
```

#### Simple

On the forum you can set a profile picture, an avatar. The attacker first uploads an ordinary
picture to see where it ends up.

#### Step by step

The browser sends the file `me.png` together with its name and the type `image/png`. The name and
the type are written by the browser, that is, by the visitor's side.

#### Deeper

An upload form is one of the most dangerous places on a site: the visitor puts a whole file on the
server, not a line of text. What happens to the file next depends on its name, where it is stored
and how the server later serves it.

### `save` The file in the web root

`server → files` · `legit` · `without-defence`
Message: me.png to web root · Result: reachable by link

```text
/var/www/html/uploads/me.png
→ /uploads/me.png
```

#### Simple

The server puts the picture into the folder the site serves its files from and **keeps the name the
visitor sent**. Now the picture opens at a direct link.

#### Step by step

The file lands in `/var/www/html/uploads/me.png`. The folder `/var/www/html` is the web root:
everything in it is reachable at the site's address.

#### Deeper

The attacker has learned two important things: the file is saved under the name he gave it and opens
at a predictable address, `/uploads/me.png`. What remains is to slip in a file the server will not send
but run.

### `save-safe` The file under a server name

`server → files` · `safe` · `with-defence`
Message: 5f1c9a.png outside · Result: outside the web root

```text
/srv/uploads/5f1c9a.png
```

#### Simple

With the defence on, the server makes up the file's name itself and puts it **outside the site's
folder**. There is no direct link to the file: the site serves the picture itself, as data.

#### Step by step

The server checked that it really is a picture, rebuilt it, gave it a random name with the `.png`
extension and saved it in `/srv/uploads`. The visitor sees the avatar at a link like
`/avatar/5f1c9a`.

#### Deeper

OWASP advises giving files names generated by the application and storing them on a separate
server, or at least outside the web root. For public access, use a handler that finds the file by its
ID.

### `shell` A script dressed as a picture

`attacker → server` · `attack`
Message: me.php, type image/png · Result: accepted

```http
POST /avatar
filename="⟦me.php⟧"
Content-Type: image/png

<?php ⟦…command from the URL…⟧ ?>
```

#### Simple

Now instead of a picture the attacker uploads **a small program** in the site's language, PHP. He
labels the file type “picture”: a server without the defence trusts that label and never looks
inside.

#### Step by step

The file name ends in `.php`, the type says `image/png`, and inside is a script that takes a command
from the request's address and runs it.

#### Deeper

The `Content-Type` is sent by the visitor, so faking it costs nothing: OWASP says plainly that it
can't be trusted. A script like this is called a web shell. In MITRE ATT&CK it is sub-technique
T1505.003.

### `store` A script in the web root

`server → files` · `attack` · `without-defence`
Message: me.php to web root · Result: attack

```text
/var/www/html/uploads/⟦me.php⟧
```

#### Simple

The server saves the file the same way as the picture: in the site's folder and under the name it
was sent with. The script is now where the site **runs** PHP files.

#### Step by step

The server checked neither the extension nor the contents. The file `me.php` sits in the web root
and is reachable at `/uploads/me.php`.

#### Deeper

This is the weakness CWE-434: the server accepts a file of a dangerous type that it then processes
itself. MITRE notes that web servers often run `.php` and `.asp` files on their own, even without an
execute permission in the file system.

### `open` A request to the script

`attacker → server` · `attack` · `without-defence`
Message: me.php, cmd=id · Result: script started

```http
GET /uploads/me.php?cmd=⟦id⟧
```

#### Simple

The attacker opens the link to his “avatar”. The server sees the `.php` extension and does not send
the file, it **runs it**.

#### Step by step

In the address the attacker passes the command `id`. The server runs the script, and the script
runs the command.

#### Deeper

Now the attacker has a remote control for the server: any command can be passed with an ordinary
request from a browser. The web shell stays in place until someone finds and removes it.

### `run` The command's answer

`server → attacker` · `attack` · `without-defence`
Message: id output · Result: server under control

```text
⟦uid=33(www-data) gid=33(www-data)⟧
```

#### Simple

The server answers with what the command printed. The attacker runs commands on the server as the
site.

#### Step by step

The answer shows the user `www-data` that the site runs as. With its rights the attacker reads
files, changes pages, looks for database passwords.

#### Deeper

This is remote code execution. Next the attacker may move into the internal network. The fewer
rights the site's account has, the less he can do.

### `check` Checking the file

`server → server` · `attack` · `with-defence` · `stopped`
Message: me.php: not an image · Result: rejected, attack failed

```text
extension: ⟦.php⟧ — only .png .jpg allowed
contents:  ⟦<?php⟧ — not a picture
```

#### Simple

Now the server checks the file instead of trusting its label. The extension is not on the short
list of allowed ones, the inside is not a picture, and the server refuses to save the file. The
attack stops here.

#### Step by step

The server matches the extension against an allowlist, checks the start of the file (PNG and JPEG
each have their own) and tries to open the picture. Any check fails, and the file is rejected.

#### Deeper

No single check is reliable on its own, OWASP warns: a file signature can be faked, an extension
hidden (`.jpg.php`, `.pHp`, `.php5`). So they are combined with the main thing: a random name from
the server and storage outside the web root. Then even a script that slips through won't run.

### `refuse` File not accepted

`server → attacker` · `safe` · `with-defence`
Message: A PNG or JPEG picture is required · Result: attack failed

#### Simple

The site answers: upload a PNG or JPEG picture. The script did not get onto the server.

#### Step by step

The attacker gets a short error. Nothing of his file is left on the server's disk.

#### Deeper

Even a real picture is better rebuilt by the server: read and saved again, without extra metadata.
OWASP notes that even this does not remove everything harmful, and the image library itself handles
untrusted data, so it is kept up to date and restricted.

## How to defend

- **Allowlist extensions.** Only what the job needs: for avatars, one or two picture formats. A
  denylist of dangerous extensions is easy to get around.
- **Don't trust `Content-Type`.** The visitor writes it. Check the file signature and contents, and
  rebuild pictures.
- **A server-chosen file name.** The server gives the file a random name, such as a UUID, instead of
  taking the one it was sent.
- **Store outside the web root.** Better still, on a separate server. Files are served by a handler
  that finds them by ID, and the server never runs them.
- **Limits and rights.** Limit the file size and the name length, allow uploads only for signed-in
  users, protect the form against CSRF.
