## Шаги

### `avatar` Новая аватарка

`attacker → server` · `legit`
Сообщение: me.png · Итог: принято

```http
POST /avatar
filename="me.png"
Content-Type: image/png
```

#### Просто

На форуме можно поставить себе картинку-аватарку. Атакующий сначала загружает обычную картинку,
чтобы посмотреть, куда она попадёт.

#### По шагам

Браузер отправляет файл `me.png` вместе с его именем и типом `image/png`. Имя и тип пишет
браузер, то есть сторона посетителя.

#### Глубже

Форма загрузки — одно из самых опасных мест сайта: посетитель кладёт на сервер целый файл, а не
строчку текста. Что будет с файлом дальше, решают имя, место хранения и то, как сервер потом его
отдаёт.

### `save` Файл в веб-корне

`server → files` · `legit` · `without-defence`
Сообщение: me.png в веб-корень · Итог: доступен по ссылке

```text
/var/www/html/uploads/me.png
→ /uploads/me.png
```

#### Просто

Сервер кладёт картинку в папку, откуда сайт раздаёт свои файлы, и **оставляет имя, которое
прислал посетитель**. Теперь картинка открывается по прямой ссылке.

#### По шагам

Файл попадает в `/var/www/html/uploads/me.png`. Папка `/var/www/html` — веб-корень: всё, что в ней
лежит, доступно по адресу сайта.

#### Глубже

Атакующий узнал две важные вещи: файл сохраняется под его именем и открывается по предсказуемому
адресу `/uploads/me.png`. Осталось подложить файл, который сервер не отдаст, а выполнит.

### `save-safe` Файл под своим именем

`server → files` · `safe` · `with-defence`
Сообщение: 5f1c9a.png вне корня · Итог: вне веб-корня

```text
/srv/uploads/5f1c9a.png
```

#### Просто

В режиме защиты сервер сам придумывает файлу имя и кладёт его **вне папки сайта**. Прямой ссылки
на файл нет: картинку отдаёт сам сайт, как данные.

#### По шагам

Сервер проверил, что это действительно картинка, пересобрал её, дал случайное имя с расширением
`.png` и сохранил в `/srv/uploads`. Посетитель видит аватарку по ссылке вроде `/avatar/5f1c9a`.

#### Глубже

OWASP советует давать файлам имена, придуманные приложением, и хранить их на отдельном сервере или
хотя бы вне веб-корня. Для открытого доступа — обработчик, который сам находит файл по номеру.

### `shell` Скрипт под видом картинки

`attacker → server` · `attack`
Сообщение: me.php, тип image/png · Итог: принято

```http
POST /avatar
filename="⟦me.php⟧"
Content-Type: image/png

<?php ⟦…команда из адреса…⟧ ?>
```

#### Просто

Теперь атакующий загружает вместо картинки **маленькую программу** на языке сайта, PHP. Тип файла
он пишет «картинка»: сервер всё равно не может проверить, правда ли это.

#### По шагам

Имя файла кончается на `.php`, тип указан как `image/png`, а внутри — скрипт, который берёт
команду из адреса запроса и выполняет её.

#### Глубже

Тип `Content-Type` присылает посетитель, поэтому подделать его ничего не стоит: OWASP прямо
говорит, что доверять ему нельзя. Такой скрипт называют веб-шеллом. В MITRE ATT&CK это подтехника
T1505.003.

### `store` Скрипт в веб-корне

`server → files` · `attack` · `without-defence`
Сообщение: me.php в веб-корень · Итог: атака

```text
/var/www/html/uploads/⟦me.php⟧
```

#### Просто

Сервер сохраняет файл, как и картинку: в папку сайта и под присланным именем. Скрипт оказался там,
откуда сайт **выполняет** файлы PHP.

#### По шагам

Сервер не проверил ни расширение, ни содержимое. Файл `me.php` лежит в веб-корне и доступен по
адресу `/uploads/me.php`.

#### Глубже

Это ошибка CWE-434: сервер принимает файл опасного типа, который потом сам обрабатывает. MITRE
отмечает, что файлы `.php` и `.asp` веб-сервер часто выполняет сам по себе, даже без права на
запуск в файловой системе.

### `open` Запрос к скрипту

`attacker → server` · `attack` · `without-defence`
Сообщение: me.php, cmd=id · Итог: скрипт запущен

```http
GET /uploads/me.php?cmd=⟦id⟧
```

#### Просто

Атакующий открывает ссылку на свой «аватар». Сервер видит расширение `.php` и не отдаёт файл, а
**запускает его**.

#### По шагам

В адресе атакующий передаёт команду `id`. Сервер выполняет скрипт, а скрипт выполняет команду.

#### Глубже

Теперь у атакующего есть пульт управления сервером: любую команду можно передать обычным запросом
из браузера. Веб-шелл остаётся на месте, пока его не найдут и не удалят.

### `run` Ответ команды

`server → attacker` · `attack` · `without-defence`
Сообщение: вывод id · Итог: сервер под контролем

```text
⟦uid=33(www-data) gid=33(www-data)⟧
```

#### Просто

Сервер отвечает тем, что напечатала команда. Атакующий выполняет команды на сервере от имени сайта.

#### По шагам

Ответ показывает пользователя `www-data`, от которого работает сайт. С его правами атакующий
читает файлы, меняет страницы, ищет пароли от базы.

#### Глубже

Это удалённое выполнение кода. Дальше атакующий может двинуться во внутреннюю сеть. Чем меньше
прав у учётной записи сайта, тем меньше он успеет.

### `check` Проверка файла

`server → server` · `attack` · `with-defence` · `stopped`
Сообщение: me.php: не картинка · Итог: отклонено, атака не сработала

```text
расширение: ⟦.php⟧ — разрешены только .png .jpg
содержимое: ⟦<?php⟧ — это не картинка
```

#### Просто

Теперь сервер проверяет файл, а не верит подписи. Расширения нет в коротком списке разрешённых,
внутри не картинка, и сервер отказывается сохранять файл. Атака останавливается здесь.

#### По шагам

Сервер сверяет расширение с белым списком, проверяет начало файла (у PNG и JPEG оно своё) и
пробует открыть картинку. Любая проверка не прошла — файл отклонён.

#### Глубже

Ни одна проверка не надёжна в одиночку, предупреждает OWASP: сигнатуру файла можно подделать,
расширение — спрятать (`.jpg.php`, `.pHp`, `.php5`). Поэтому их сочетают с главным: случайным
именем от сервера и хранением вне веб-корня. Даже пропущенный скрипт тогда не запустится.

### `refuse` Файл не принят

`server → attacker` · `safe` · `with-defence`
Сообщение: Нужна картинка PNG или JPEG · Итог: атака не удалась

#### Просто

Сайт отвечает: загрузите картинку PNG или JPEG. Скрипт на сервер не попал.

#### По шагам

Атакующий получает короткую ошибку. На диске сервера от его файла ничего не осталось.

#### Глубже

Даже настоящую картинку сервер лучше пересобрать: прочитать и сохранить заново, без лишних
метаданных. OWASP оговаривается, что и это не убирает всё вредное, а сама библиотека картинок
работает с чужими данными, поэтому её держат обновлённой и ограниченной.

## Как защититься

- **Белый список расширений.** Только то, что нужно делу: для аватарок — один-два формата
  картинок. Чёрный список опасных расширений легко обойти.
- **Не верить `Content-Type`.** Его пишет посетитель. Проверяйте сигнатуру файла и содержимое, а
  картинки пересобирайте.
- **Своё имя файла.** Сервер даёт файлу случайное имя, например UUID, а не берёт присланное.
- **Хранить вне веб-корня.** Лучше на отдельном сервере. Файлы отдаёт обработчик, который находит их
  по номеру, и сервер их никогда не выполняет.
- **Пределы и права.** Ограничьте размер файла, длину имени, загрузку разрешите только вошедшим
  пользователям, защитите форму от CSRF.
