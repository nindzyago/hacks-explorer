## Шаги

### `visit` Атакующий получает сессию

`attacker → server` · `legit`
Сообщение: GET /login · Итог: выдан sid K7Q2

```http
HTTP/1.1 200 OK
Set-Cookie: sid=K7Q2…
```

#### Просто

Сайт помнит посетителя по **номеру сессии** — длинной случайной строке в cookie. Атакующий просто
заходит на страницу входа, и сайт выдаёт ему такой номер: `K7Q2…`. Войти он ещё не вошёл.

#### По шагам

Сервер заводит сессию ещё до входа: например, чтобы помнить корзину. Номер он отправляет в
заголовке `Set-Cookie`, браузер прикладывает его к каждому следующему запросу.

#### Глубже

Пока человек не вошёл, сессия ничего не стоит. Ценной она становится в момент входа: сервер
отмечает в ней «это Анна». Кто знает номер такой сессии, для сайта и есть Анна — пароль ему уже не
нужен.

### `plant` Подброшенная ссылка

`attacker → user` · `attack`
Сообщение: ссылка с чужим sid · Итог: Анна открыла

```text
https://shop.example/login?sid=⟦K7Q2…⟧
```

#### Просто

Атакующий присылает Анне ссылку на настоящий сайт магазина. Но в ссылку вписан **его** номер
сессии. Анна видит знакомый адрес и открывает её.

#### По шагам

Этот сайт умеет брать номер сессии из адреса страницы, а не только из cookie. Поэтому браузер
Анны теперь работает в сессии `K7Q2…`, номер которой атакующий знает заранее.

#### Глубже

Это и есть **фиксация** сессии: атакующий не крадёт номер, а заранее навязывает свой. MITRE
перечисляет и другие способы подбросить номер: через XSS, через соседний сайт на том же домене,
который ставит cookie на весь домен.

### `login` Анна входит

`user → server` · `legit`
Сообщение: логин и пароль · Итог: пароль верный

```http
POST /login
Cookie: sid=K7Q2…

login=anna&password=…
```

#### Просто

Анна вводит свой логин и пароль. Всё честно: пароль знает только она, атакующий его не видит.

#### По шагам

Запрос на вход идёт с подброшенным номером сессии. Сервер проверяет пароль, он верный.

#### Глубже

Ни пароль, ни второй фактор тут не помогают: атака начинается **после** успешного входа. Важно
только одно — что сервер сделает с номером сессии, когда Анна вошла.

### `keep` Номер остался прежним

`server → user` · `attack` · `without-defence`
Сообщение: вход, sid тот же · Итог: K7Q2 — сессия Анны

```http
HTTP/1.1 302 Found
Location: /account
```

#### Просто

Сервер пишет «добро пожаловать» и отмечает в сессии `K7Q2…`, что это **Анна**. Номер сессии он не
меняет.

#### По шагам

Новой cookie в ответе нет. Сессия, номер которой знает атакующий, стала сессией вошедшей Анны.

#### Глубже

В каталоге MITRE это CWE-384 «Session Fixation»: пользователь входит, а существующий номер сессии
не отменяется. В OWASP Top 10:2021 повтор номера сессии после успешного входа назван среди ошибок
пункта A07 «Identification and Authentication Failures».

### `rotate` Новый номер после входа

`server → user` · `safe` · `with-defence`
Сообщение: вход, новый sid · Итог: K7Q2 удалён

```http
HTTP/1.1 302 Found
Set-Cookie: sid=⟦Z9M4…⟧; Secure; HttpOnly; SameSite=Lax
```

#### Просто

После входа сервер выдаёт Анне **совсем новый номер** сессии, а старый `K7Q2…` уничтожает.
Номер, который знал атакующий, больше ничего не значит.

#### По шагам

Новый номер случайный, его никто не видел. Старая сессия удалена на сервере, а не только в
браузере.

#### Глубже

OWASP требует менять номер сессии при любой смене уровня прав, и вход — самый частый такой случай.
Атрибуты cookie защищают от кражи: `Secure` — отправлять только по HTTPS, `HttpOnly` — не
показывать скриптам страницы (RFC 6265), `SameSite` — не прикладывать к запросам с чужих сайтов.

### `replay` Атакующий заходит

`attacker → server` · `attack` · `without-defence`
Сообщение: старый sid K7Q2 · Итог: вошёл как Анна

```http
GET /account
Cookie: sid=⟦K7Q2…⟧
```

#### Просто

Атакующий открывает сайт со **своим старым номером** сессии. Сервер видит сессию Анны и
показывает её личный кабинет: адрес, заказы, сохранённые карты.

#### По шагам

Пароль не нужен: для сервера номер сессии и есть пропуск. Атакующий действует от имени Анны,
пока сессия не закончится.

#### Глубже

Тот же итог даёт и **кража** сессии: номер утекает через XSS, если cookie без `HttpOnly`, по
открытому HTTP без `Secure`, через вредоносную программу на компьютере жертвы или через фишинговый
прокси. В MITRE ATT&CK кража — T1539, а вход с чужой cookie — T1550.004; там отмечено, что так
можно обойти и второй фактор.

### `refused` Сессии больше нет

`attacker → server` · `attack` · `with-defence` · `stopped`
Сообщение: старый sid K7Q2 · Итог: атака не сработала

```http
GET /account
Cookie: sid=⟦K7Q2…⟧
```

#### Просто

Атакующий приходит со старым номером, но такой сессии **больше нет**. Сервер просит войти, а
пароля Анны у атакующего нет.

#### По шагам

Сервер не находит `K7Q2…` среди живых сессий и отправляет посетителя на страницу входа.
Подозрительную попытку стоит записать в журнал.

#### Глубже

Ещё раньше атаку останавливает строгий режим: сервер принимает только номера, которые выдал сам,
и только из cookie, а не из адреса страницы. OWASP предупреждает, что номер в адресе утекает через
историю, журналы и заголовок Referer и помогает фиксации.

## Как защититься

- **Новый номер сессии после входа.** Сервер выдаёт новый случайный номер при входе и при любой
  смене прав, а старый уничтожает. Это главная защита от фиксации.
- **Номер только в cookie.** Номер сессии не принимается из адреса страницы и полей формы, а
  неизвестные сервер не принимает вовсе — только те, что выдал сам.
- **Атрибуты cookie.** `Secure`, `HttpOnly` и `SameSite=Strict` или `Lax` затрудняют кражу через
  открытую сеть, XSS и чужие сайты.
- **Длинные случайные номера.** Не меньше 64 бит случайности из криптографического генератора,
  чтобы номер нельзя было угадать.
- **Сессия заканчивается.** Тайм-ауты при бездействии и общий предел жизни сессии; при выходе
  сессия уничтожается на сервере.
