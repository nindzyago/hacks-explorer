## Шаги

### `burst` Два запроса в одно мгновение

`attacker → server` · `attack`
Сообщение: 2 × применить промокод · Итог: оба приняты

```http
POST /cart/promo     code=WELCOME500
POST /cart/promo     code=WELCOME500
⟦оба отправлены в одну и ту же миллисекунду⟧
```

#### Просто

Магазин дарит новичкам **промокод** на 500 рублей — один раз. Атакующий отправляет два запроса
«применить промокод» **одновременно**, как будто нажал кнопку двумя руками сразу.

#### По шагам

Обычно второй запрос пришёл бы позже первого и получил бы ответ «код уже использован». Но здесь
оба приходят почти в одно мгновение. Сервер магазина обрабатывает запросы параллельно, поэтому
берётся за оба сразу.

#### Глубже

Такая ошибка называется **гонкой**: результат зависит от того, какой из параллельных обработчиков
успеет первым. Окно для гонки может длиться миллисекунды, поэтому атакующие отправляют сразу много
одинаковых запросов: чем больше, тем вероятнее попасть в окно.

### `check` Обе проверки говорят «код свободен»

`server → db` · `attack` · `without-defence`
Сообщение: 2 × SELECT used · Итог: оба раза false

```sql
SELECT used FROM promo_codes WHERE code = 'WELCOME500'
-- обработчик 1: used = false
-- обработчик 2: ⟦used = false⟧
```

#### Просто

Каждый обработчик сначала **спрашивает** базу: «код ещё не использован?» Оба спрашивают раньше,
чем кто-то успел его отметить, и оба слышат: «свободен».

#### По шагам

Код написан в два шага: сначала проверить, потом действовать. Между проверкой и действием есть
промежуток, и в него успевает влезть второй обработчик со своей проверкой. Каждая проверка
по отдельности честная, просто ответ устаревает, не дожив до действия.

#### Глубже

MITRE называет это TOCTOU, *time-of-check time-of-use* (CWE-367): состояние ресурса проверили,
а к моменту использования оно уже другое. Это частный случай CWE-362: общий ресурс, к которому
код должен обращаться монопольно, но не обращается.

### `apply` Обе скидки записаны

`server → db` · `attack` · `without-defence`
Сообщение: 2 × UPDATE и скидка · Итог: код отмечен, скидка дважды

```sql
UPDATE promo_codes SET used = true WHERE code = 'WELCOME500'
INSERT INTO discounts (cart, amount) VALUES (77, 500)
⟦INSERT INTO discounts (cart, amount) VALUES (77, 500)⟧
```

#### Просто

Оба обработчика уверены, что код свободен. Каждый отмечает его как использованный и **добавляет
скидку**. Отметка ставится дважды — это не страшно, а скидки две.

#### По шагам

Второе `UPDATE` ничего не меняет: `used` и так уже `true`. Но `INSERT` скидки выполняется в
обоих обработчиках, ведь своё решение каждый принял раньше, по устаревшему ответу.

#### Глубже

Чем больше работы между проверкой и записью (запрос к другому сервису, расчёт корзины), тем шире
окно. Код, который выглядит правильным при последовательных запросах, ломается только при
одновременных, поэтому такие ошибки трудно заметить в обычных тестах.

### `double` Скидка в два раза больше

`server → attacker` · `attack` · `without-defence`
Сообщение: 2 × «скидка применена» · Итог: 1000 рублей вместо 500

```text
Корзина 77: скидка ⟦500 + 500⟧ = 1000
```

#### Просто

Атакующий получает **две скидки** по одному одноразовому коду. Если отправить десять запросов
разом, скидок может оказаться больше.

#### По шагам

Оба ответа сообщают «скидка применена», и в корзине теперь две строки скидки. Магазин потерял
деньги, и в журнале всё выглядит как два обычных запроса.

#### Глубже

Тот же приём работает везде, где действие должно случиться ограниченное число раз: подарочные
карты, бонусы за приглашение, вывод денег со счёта, голосование. OWASP в WSTG-BUSL-05 советует
проверять, можно ли применить одну скидку несколько раз.

### `claim` Первый обработчик забирает код атомарно

`server → db` · `safe` · `with-defence`
Сообщение: UPDATE с условием · Итог: изменена 1 строка

```sql
UPDATE promo_codes SET used = true
WHERE code = 'WELCOME500' AND used = false
-- изменено строк: 1 → скидку добавить
```

#### Просто

Теперь проверка и отметка — **одна команда**. База сама следит, чтобы её не выполнили два
обработчика наполовину каждый. Первый успел: код его, скидка добавляется.

#### По шагам

Условие `used = false` стоит прямо в `UPDATE`. База меняет строку, только если код ещё свободен,
и сообщает, сколько строк изменила. Одна строка — значит, этот обработчик и забрал код.

#### Глубже

CWE-362 советует атомарные операции и примитивы синхронизации. В базе это условное `UPDATE`,
транзакция с блокировкой строки или ограничение `UNIQUE` на паре «код — заказ», которое не даст
записать вторую скидку.

### `second` Второй обработчик получает ноль строк

`server → db` · `attack` · `with-defence` · `stopped`
Сообщение: тот же UPDATE · Итог: изменено 0 строк, атака не сработала

```sql
UPDATE promo_codes SET used = true
WHERE code = 'WELCOME500' AND ⟦used = false⟧
-- изменено строк: 0 → код уже использован
```

#### Просто

Второй обработчик пытается забрать тот же код, но база отвечает: **ноль строк** — код уже не
свободен. Скидку он не добавляет. Здесь атака и останавливается.

#### По шагам

Распространённые реляционные базы выполняют два `UPDATE` одной строки по очереди: второй ждёт,
пока первый закончит, и видит уже `used = true`. Условие не выполнено, строка не меняется.

#### Глубже

Важно, что проверка не отделена от действия: нет промежутка, в который мог бы влезть второй
обработчик. Блокировка в самом приложении, внутри одного процесса, тут ненадёжна: у магазина
бывает несколько серверов, а общая у них только база.

### `once` Одна скидка и честный отказ

`server → attacker` · `safe` · `with-defence`
Сообщение: «применён» и «уже использован» · Итог: скидка 500 рублей

```text
запрос 1: скидка 500 применена
запрос 2: промокод уже использован
```

#### Просто

Атакующий получает одну скидку, как и все. Второй запрос получает обычный отказ.

#### По шагам

Ответы такие же, как если бы запросы пришли по очереди. Сколько бы одновременных запросов ни
пришло, код сработает ровно один раз.

#### Глубже

От случайных повторов, когда браузер или сеть отправили запрос ещё раз, помогает ключ
идемпотентности: сервер запоминает ключ и на повтор отвечает прежним результатом. RFC 9110,
раздел 9.2.2: `POST` не идемпотентен, повтор может сработать второй раз, поэтому защита нужна на
стороне сервера.

## Как защититься

- **Проверка и действие — одна операция.** Условное `UPDATE … WHERE used = false` с проверкой числа
  изменённых строк, транзакция с блокировкой строки или ограничение `UNIQUE` в базе.
- **Общий ресурс охраняет тот, кто общий.** Блокировка в памяти одного процесса не поможет, если
  серверов несколько. Защищайте там, где лежат данные.
- **Лимиты на сервере.** Сколько раз можно применить код, бонус или вывести деньги, решает сервер,
  а не кнопка, которая блокируется после нажатия.
- **Ключ идемпотентности.** Для операций с деньгами повтор того же запроса возвращает прежний
  результат, а не выполняется снова.
- **Тестируйте одновременность.** Отправьте на тестовую копию десятки одинаковых запросов разом и
  проверьте, что одноразовое действие сработало один раз.
