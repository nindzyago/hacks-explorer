# Отравление веб-кэша

`lesson` E2 · `section` E · `wave` 1 · `format` 1

## Паспорт

- `severity` high
- `impact` Вредный ответ из кэша получают все посетители страницы, хотя сами ничего подозрительного не отправляли
- `defence` Адреса из настроек сайта, а не из заголовков запроса; всё, что влияет на ответ, входит в ключ кэша
- `class` Подмена ответа в общем кэше

## Шаги

### `send` Запрос с лишним заголовком

`attacker → cache` · `attack`
Сообщение: GET /news + чужой заголовок · Итог: в кэше нет, запрос идёт дальше

```http
GET /news
Host: news.example
⟦X-Forwarded-Host: evil.example⟧
```

#### Просто

Перед сайтом новостей стоит **кэш**: он запоминает готовые страницы и сам раздаёт их посетителям,
чтобы сервер не собирал одну и ту же страницу тысячу раз. Атакующий запрашивает главную страницу
новостей и дописывает в запрос **лишний заголовок** со своим доменом.

#### По шагам

Кэш ищет у себя сохранённый ответ по **ключу кэша**: метод и адрес, здесь `GET` и
`news.example/news`. Заголовок `X-Forwarded-Host` в ключ не входит, кэш на него даже не смотрит.
Свежей копии нет, поэтому кэш передаёт запрос серверу целиком, вместе с заголовком атакующего.

#### Глубже

RFC 9111, раздел 2: ключ кэша состоит как минимум из метода и адреса запроса. Заголовки запроса
стандарт добавляет к ключу через заголовок ответа `Vary` (раздел 4.1). Всё, что меняет ответ, но не
входит в ключ, — дыра: два разных запроса получат одну запись. Атакующий
выбирает момент, когда старая копия истекла, чтобы его запрос оказался первым.

### `forward` Кэш передаёт запрос серверу

`cache → server` · `attack` · `without-defence`
Сообщение: GET /news + X-Forwarded-Host · Итог: сервер поверил заголовку

```http
GET /news
Host: news.example
⟦X-Forwarded-Host: evil.example⟧
```

#### Просто

Сервер получает запрос и видит заголовок `X-Forwarded-Host`. Он думает: «наверное, меня открыли
под другим именем, буду строить ссылки от него» — и **верит** чужому значению.

#### По шагам

Такой заголовок обычно ставит прокси перед сервером, чтобы сообщить, какое имя сайта набрал
посетитель. Сервер news.example берёт из него домен для адреса своего скрипта. По самому
заголовку сервер не может понять, поставил ли его свой прокси или прислал посетитель.

#### Глубже

По MDN, `X-Forwarded-Host` — стандарт де-факто, ни в одной спецификации его нет; стандартная замена —
заголовок `Forwarded` из RFC 7239. Сам RFC 7239 предупреждает: любое звено по пути, включая
клиента, может такой заголовок изменить, поэтому полагаться на него нельзя (раздел 8.1).

### `reflect` Ответ со скриптом атакующего попадает в кэш

`server → cache` · `attack` · `without-defence`
Сообщение: страница новостей · Итог: сохранена в кэше на 5 минут

```text
Cache-Control: max-age=300
<script src="https://⟦evil.example⟧/app.js"></script>
```

#### Просто

Сервер собирает страницу, где главный скрипт грузится **с домена атакующего**. Кэш не знает, что
страница испорчена, и **запоминает** её для всех.

#### По шагам

Ответ разрешает хранить себя 300 секунд (`max-age=300`). Кэш кладёт его под ключ
`GET news.example/news` — тот же, под которым ищут страницу все посетители. Заголовок, из-за
которого ответ стал другим, в ключе не отмечен.

#### Глубже

RFC 9111 в разделе 7.1 называет это отравлением кэша: вредный ответ, попавший в кэш, бьёт по
многим пользователям сразу. Через подменённое имя хоста страница может испортиться по-разному:
ссылка на скрипт, адрес перенаправления, ссылка на стили. Опасно всё, что сервер строит из
заголовков, которые кэш не учитывает.

### `visit` Посетитель открывает новости

`browser → cache` · `legit`
Сообщение: GET /news · Итог: копия есть в кэше

```http
GET /news
Host: news.example
```

#### Просто

Обычный читатель открывает сайт новостей. Его запрос совершенно чистый: никаких странных
заголовков.

#### По шагам

Кэш вычисляет ключ: `GET news.example/news`. Под этим ключом уже лежит свежая копия, поэтому до
сервера запрос не доходит.

#### Глубже

Жертве не нужно ни переходить по странной ссылке, ни что-то нажимать: OWASP в WSTG-INPV-17
подчёркивает, что пострадавшие получают отравленный ответ, хотя сами ничего вредного не отправляли.
Это отличает отравление кэша от отражённого XSS.

### `serve` Кэш раздаёт отравленную страницу

`cache → browser` · `attack` · `without-defence`
Сообщение: страница из кэша · Итог: скрипт атакующего у каждого читателя

```html
<script src="https://⟦evil.example⟧/app.js"></script>
```

#### Просто

Читатель получает испорченную страницу, и его браузер загружает **скрипт атакующего**. Так
происходит с каждым, кто откроет новости, пока копия не истечёт.

#### По шагам

Браузер видит тег `<script>` с адресом на evil.example и выполняет загруженный код как часть сайта
новостей: читать страницу, отправлять запросы от имени читателя, показывать поддельные формы.

#### Глубже

Через 5 минут копия истечёт, но атакующий может повторять свой запрос снова и снова, чтобы каждый
раз оказаться первым. Один запрос раз в несколько минут — и страница отравлена для всей аудитории.

### `ignore` Сервер не верит заголовку

`cache → server` · `attack` · `with-defence` · `stopped`
Сообщение: GET /news + X-Forwarded-Host · Итог: заголовок не используется, атака не сработала

```text
адрес сайта в настройках: https://news.example
⟦X-Forwarded-Host: evil.example⟧  → не используется
```

#### Просто

Сервер берёт имя сайта **из своих настроек**, а не из заголовков запроса. Что бы ни прислал
посетитель, ссылки ведут на news.example. Здесь атака и останавливается.

#### По шагам

Адрес сайта записан в конфигурации один раз. Заголовок `X-Forwarded-Host` сервер берёт только от
своего прокси, который затирает присланное посетителем значение, и только если значение есть в
списке разрешённых имён, иначе не учитывает.

#### Глубже

Второй слой — на стороне кэша. Он может убирать из запроса заголовки, которые сервер не должен
видеть, или включать в ключ всё, что влияет на ответ: для этого сервер перечисляет такие заголовки
в `Vary`. Тогда разные запросы получают разные записи, и чужая копия не достаётся никому.

### `clean` Чистая страница в кэше

`server → cache` · `safe` · `with-defence`
Сообщение: страница новостей · Итог: сохранена, ссылки на свой домен

```html
<script src="https://news.example/app.js"></script>
```

#### Просто

Сервер отдаёт обычную страницу, где скрипт грузится с самого сайта. Кэш её сохраняет, и это
безопасно.

#### По шагам

Ответ не зависит от заголовка атакующего: на любой запрос к `/news` сервер собирает одну и ту же
страницу. Значит, одна запись на всех — правильное поведение кэша.

#### Глубже

Правило простое: под одним ключом кэша должен лежать ответ, одинаковый для всех запросов с этим
ключом. Если ответ всё же различается, это различие должно попасть в ключ или ответ не должен
кэшироваться.

### `serve-clean` Посетитель получает настоящую страницу

`cache → browser` · `safe` · `with-defence`
Сообщение: страница из кэша · Итог: только скрипты сайта

```html
<script src="https://news.example/app.js"></script>
```

#### Просто

Читатель получает страницу из кэша быстро, как и задумано, и в ней нет ничего чужого.

#### По шагам

Браузер загружает скрипт с news.example. Попытка атакующего не оставила следа: в кэше лежит та же
страница, что получил бы любой другой посетитель.

#### Глубже

Страницы, которые зависят от посетителя (личный кабинет, корзина), вообще не стоит класть в общий
кэш: для этого ответ помечается `Cache-Control: private` или `no-store`.

## Как защититься

- **Адреса из настроек.** Имя сайта для ссылок, скриптов и перенаправлений берите из конфигурации,
  а не из заголовков `Host`, `X-Forwarded-Host` и `Forwarded`.
- **Не верьте пересылочным заголовкам.** Учитывайте их, только если их поставил ваш прокси, и
  сверяйте значение со списком разрешённых имён. Пусть прокси стирает такие заголовки, пришедшие
  снаружи.
- **Всё, что меняет ответ, — в ключ кэша.** Если ответ зависит от заголовка, перечислите его в `Vary`
  или настройте ключ кэша так, чтобы разные запросы не делили одну запись.
- **Личное не в общий кэш.** Ответы, разные для разных людей, помечайте `Cache-Control: private` или
  `no-store`.
- **Проверьте связку целиком.** Отправьте запрос с чужим `X-Forwarded-Host` на тестовую копию и
  посмотрите, не изменилась ли страница, которую затем видят другие.
