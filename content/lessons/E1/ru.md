## Шаги

### `smuggle` Запрос с двумя длинами

`attacker → proxy` · `attack` · `without-defence`
Сообщение: POST с двумя длинами · Итог: принят

```http
POST / HTTP/1.1
Host: shop.example
⟦Content-Length: 62⟧
⟦Transfer-Encoding: chunked⟧

0

⟦GET /settings/email?new=x@evil.example HTTP/1.1⟧
⟦X-Skip: ⟧
```

#### Просто

Длину тела запроса в HTTP/1.1 можно указать **двумя способами**: числом байт в `Content-Length`
или кусками (`chunked`), где пустой кусок `0` значит «конец». Атакующий указывает **оба** — и
они говорят разное.

#### По шагам

По `Content-Length` тело — всё до последней строки. По кускам тело кончается сразу на `0`, а
дальше начинается **второй запрос**, спрятанный внутри первого. Он не дописан: последняя строка
обрывается на заголовке `X-Skip:`.

#### Глубже

Это вариант, который называют CL.TE: прокси верит `Content-Length`, сервер — `Transfer-Encoding`.
Бывает и наоборот (TE.CL), и с хитро записанным `Transfer-Encoding`, который один участник
узнаёт, а другой нет. Технику описали в 2005 году Линхарт, Кляйн, Хелед и Оррин, на их работу
ссылается RFC 9112 (раздел 11.2).

### `cl` Прокси видит один запрос

`proxy → server` · `attack` · `without-defence`
Сообщение: один запрос · Итог: передано

```text
прокси: Content-Length: 62 → один запрос целиком
```

#### Просто

**Прокси** стоит перед сервером: принимает запросы из интернета и пересылает их серверу. Он верит
`Content-Length` и видит **один** обычный запрос к `/`. Ничего подозрительного.

#### По шагам

Чтобы не открывать соединение на каждый запрос, прокси держит с сервером несколько постоянных
соединений и шлёт по ним запросы **разных посетителей** подряд.

#### Глубже

Граница между запросами в таком соединении — только длина тела. Если прокси и сервер считают
её по-разному, они перестают понимать, где кончается один запрос и начинается следующий. MITRE
называет это CWE-444 «Inconsistent Interpretation of HTTP Requests».

### `te` Сервер видит полтора запроса

`server → server` · `attack` · `without-defence`
Сообщение: конец на 0 · Итог: хвост ждёт

```text
сервер: Transfer-Encoding: chunked → тело кончилось на 0
остаток: ⟦GET /settings/email?new=x@evil.example …⟧
```

#### Просто

**Сервер** верит кускам. Для него тело кончилось на `0`, и он отвечает на запрос к `/`. Хвост с
`GET /settings/email` остаётся в соединении — как **начало следующего запроса**.

#### По шагам

Начало ждёт продолжения. Следующие байты, которые придут по этому соединению, сервер приклеит к
нему.

#### Глубже

RFC 9112 (раздел 6.3) решает спор так: если есть оба заголовка, `Transfer-Encoding` главнее
`Content-Length`. Но тут же предупреждает, что такое сообщение может быть попыткой контрабанды
запроса, и с ним следует обращаться как с ошибкой. Посредник, который всё же пересылает его
дальше, обязан убрать `Content-Length`. Прокси из урока этого не сделал.

### `anna` Анна открывает корзину

`user → proxy` · `legit`
Сообщение: GET /cart с куками · Итог: принято

```http
GET /cart HTTP/1.1
Host: shop.example
Cookie: session=anna…
```

#### Просто

Анна ничего не подозревает: она открывает **свою корзину**. Браузер прикладывает её куки сессии.

#### По шагам

Прокси принимает обычный запрос и отправляет его серверу — по тому же постоянному соединению,
где лежит хвост атакующего.

#### Глубже

Атакующему не нужно знать, кто придёт следующим. Он повторяет свой запрос, пока хвост не
достанется кому-нибудь, кто вошёл в аккаунт.

### `glued` Запрос Анны приклеен к чужому

`proxy → server` · `attack` · `without-defence`
Сообщение: склейка · Итог: почта Анны сменена

```http
GET /settings/email?new=x@evil.example HTTP/1.1
X-Skip: ⟦GET /cart HTTP/1.1⟧
Host: shop.example
Cookie: ⟦session=anna…⟧
```

#### Просто

Сервер склеивает хвост и запрос Анны в **один**. Строка «GET /cart» Анны ушла в значение
заголовка `X-Skip`, а её куки достались спрятанному запросу. Сервер меняет **почту Анны** на
адрес атакующего.

#### По шагам

Теперь атакующий может попросить сброс пароля на свою почту и забрать аккаунт. Анна получает
странный ответ вместо корзины и, скорее всего, просто обновит страницу.

#### Глубже

Смена почты обычным GET — лишняя слабость этого вымышленного магазина, она здесь для
краткости. Контрабанда работает с любым действием, которое сервер выполняет по куке. Бывает и
иначе: прокси пропускает спрятанный запрос к странице, которую сам запрещает снаружи, ведь
он этого запроса не видел.

### `reject` Прокси отвергает две длины

`attacker → proxy` · `attack` · `with-defence` · `stopped`
Сообщение: POST с двумя длинами · Итог: атака не сработала

```http
POST / HTTP/1.1
⟦Content-Length: 62⟧
⟦Transfer-Encoding: chunked⟧
```

#### Просто

Прокси видит **оба заголовка длины** сразу и не гадает, какому верить. Запрос до сервера не
доходит.

#### По шагам

Прокси не пересылает такой запрос и закрывает соединение с атакующим. Хвосту негде остаться.

#### Глубже

RFC 9112 разрешает серверу отвергнуть запрос, где есть и `Content-Length`, и
`Transfer-Encoding` (раздел 6.1), и в любом случае требует закрыть соединение после ответа на
него. Надёжнее всего, когда прокси и сервер — одна и та же строгая реализация или между ними
HTTP/2: там длина задаётся кадрами протокола, а `Transfer-Encoding` запрещён (RFC 9113, раздел
8.2.2).

### `refuse` Ответ 400

`proxy → attacker` · `safe` · `with-defence`
Сообщение: 400, соединение закрыто · Итог: хвоста нет

```http
HTTP/1.1 400 Bad Request
Connection: close
```

#### Просто

Атакующий получает **ошибку 400**, соединение закрыто. В очереди к серверу ничего не осталось.

#### По шагам

Попытка видна в журнале прокси: обычные браузеры двух заголовков длины не присылают.

#### Глубже

Если прокси принимает HTTP/2 снаружи, а к серверу говорит по HTTP/1.1, контрабанда возможна при
переводе запроса. RFC 9113 (раздел 8.1.1) велит считать запрос испорченным, если
`content-length` не совпадает с суммой длин кадров DATA, а посредникам — не пересылать такие
запросы.

### `clean` Запрос Анны приходит один

`proxy → server` · `safe` · `with-defence`
Сообщение: GET /cart · Итог: Анна видит корзину

```http
GET /cart HTTP/1.1
Host: shop.example
Cookie: session=anna…
```

#### Просто

Запрос Анны приходит к серверу **сам по себе**, без чужого начала. Анна видит свою корзину, её
почта на месте.

#### По шагам

Прокси и сервер одинаково видят границы запросов, поэтому по общему соединению не просочится
ничего лишнего.

#### Глубже

Проверять стоит всю цепочку: CDN, балансировщик, прокси и сервер могут быть разными программами.
Достаточно одного звена, которое читает границу запроса не так, как соседнее.

## Как защититься

- **Отвергать двусмысленные запросы.** Запрос с `Content-Length` и `Transfer-Encoding` сразу,
  с двумя разными `Content-Length` или с непонятным `Transfer-Encoding` получает 400, а
  соединение закрывается.
- **HTTP/2 до самого сервера.** Длину задают кадры протокола, а не заголовки; `Transfer-Encoding`
  в HTTP/2 запрещён.
- **Строгий перевод HTTP/2 → HTTP/1.1.** Прокси проверяет `content-length` по кадрам и не
  пропускает в заголовки переводы строк.
- **Одинаковое понимание по всей цепочке.** Прокси и сервер обновлены и настроены по RFC 9112;
  лучше одна и та же реализация разбора.
- **Без общих соединений, если сомневаетесь.** Отдельное соединение на запрос дороже, но хвосту
  некуда приклеиться.
