# Ошибки OAuth

`lesson` D5 · `section` D · `wave` 3 · `format` 1

## Шаги

### `start` Вход через сервис входа

`user → client` · `legit`
Сообщение: «Войти через ID» · Итог: переход на id.example

```text
https://id.example/authorize
  ?client_id=print
  &redirect_uri=https://print.example/cb
  &state=…
```

#### Просто

Анна заходит на сайт фотопечати и нажимает «Войти через ID». Пароль от печати ей не нужен: за неё
поручится **сервис входа**, где у неё уже есть аккаунт.

#### По шагам

Сайт отправляет браузер Анны на `id.example` и говорит: «я — приложение `print`, верни
пользователя вот по этому адресу». Этот адрес возврата называется `redirect_uri`.

#### Глубже

Так работает **OAuth 2.0** (RFC 6749) в варианте с кодом авторизации. Сервис входа отдаёт
приложению не пароль, а одноразовый **код**, и приложение меняет его на токен доступа. Адрес
возврата приложение заранее зарегистрировало у сервиса входа: `https://print.example/cb`.

### `bait` Ссылка с чужим адресом возврата

`attacker → user` · `attack`
Сообщение: ссылка · Итог: Анна открыла

```text
https://id.example/authorize
  ?client_id=print
  &redirect_uri=⟦https://print.example.evil.example/cb⟧
```

#### Просто

Атакующий присылает Анне ссылку на **настоящий** сервис входа. Всё в ней как обычно, кроме адреса
возврата: он ведёт на сайт атакующего.

#### По шагам

Адрес `print.example.evil.example` начинается так же, как настоящий, но это другой домен — он
принадлежит атакующему. Анна видит знакомую страницу `id.example` и подвоха не замечает.

#### Глубже

RFC 6749 (раздел 10.6) описывает именно эту атаку: атакующий подменяет адрес возврата в запросе
на вход и заставляет жертву открыть такую ссылку. Сервис входа покажет жертве обычный запрос от
знакомого приложения.

### `loose` Сравнение по началу адреса

`user → idp` · `attack` · `without-defence`
Сообщение: чужой адрес · Итог: адрес принят

```text
зарегистрирован: https://print.example
пришёл:          ⟦https://print.example.evil.example/cb⟧
```

#### Просто

Сервис входа проверяет адрес возврата **небрежно**: только то, что он начинается с
зарегистрированного. Чужой адрес эту проверку проходит.

#### По шагам

Анна уже вошла в `id.example` раньше, поэтому сервис сразу спрашивает: «Разрешить Фотопечати
доступ?» Анна нажимает «Разрешить» — она ведь и правда пользуется этой печатью.

#### Глубже

RFC 9700 (раздел 4.1) разбирает, как сравнение по шаблону или по части адреса приводит к краже
кода, и отмечает, что такие ошибки находили на настоящих сервисах. В каталоге MITRE близкая
слабость — CWE-601 «URL Redirection to Untrusted Site»: перенаправление на адрес, который прислал
пользователь.

### `exact` Точное сравнение адреса

`user → idp` · `attack` · `with-defence` · `stopped`
Сообщение: чужой адрес · Итог: атака не сработала

```text
зарегистрирован: https://print.example/cb
пришёл:          ⟦https://print.example.evil.example/cb⟧
```

#### Просто

Сервис входа сравнивает адрес возврата с зарегистрированным **целиком, знак в знак**. Адреса не
совпали — сервис дальше не идёт.

#### По шагам

Сравнивается вся строка, без шаблонов и без «начинается с». Любое отличие — отказ, и код вообще
не создаётся.

#### Глубже

RFC 9700 (раздел 2.1) требует от сервиса входа точного сравнения строк. Исключение одно: порт в
адресе `localhost` у приложений на компьютере и телефоне. Такая проверка проще шаблонов и не
оставляет щелей.

### `leak` Код уезжает к атакующему

`idp → attacker` · `attack` · `without-defence`
Сообщение: код Анны · Итог: код у атакующего

```http
HTTP/1.1 302 Found
Location: https://print.example.evil.example/cb?code=⟦SplxlO…⟧
```

#### Просто

Сервис входа отправляет браузер Анны по адресу возврата — то есть к атакующему. С собой браузер
везёт **код авторизации** Анны.

#### По шагам

Браузер выполняет перенаправление сам, Анна видит лишь мелькнувшую страницу. Сайт атакующего
записывает код из адреса.

#### Глубже

Код живёт недолго: RFC 6749 советует срок не больше 10 минут и разрешает использовать код только
один раз. Атакующему этого хватает — код он пустит в дело сразу.

### `inject` Код подсунут Фотопечати

`attacker → client` · `attack` · `without-defence`
Сообщение: /cb с кодом Анны · Итог: принято

```http
GET /cb?code=⟦SplxlO…⟧
Host: print.example
```

#### Просто

Атакующий сам открывает **настоящий** адрес возврата Фотопечати и подставляет туда украденный
код. Фотопечать думает, что это обычное возвращение с сервиса входа.

#### По шагам

Атакующий заранее начал свой вход на Фотопечати, поэтому у него есть своя сессия на сайте. В
ответ сервиса входа он вписывает код Анны вместо своего.

#### Глубже

RFC 9700 (раздел 4.5) называет это внедрением кода авторизации. Обычно его останавливает
**PKCE** (RFC 7636): приложение при начале входа придумывает секрет `code_verifier`, а в запрос
кладёт только его хеш, и код привязан к этому хешу. Но здесь запрос на вход составил атакующий и
мог вписать хеш из своей сессии на Фотопечати: RFC 9700 (раздел 4.5.4) признаёт такой обход.
Поэтому главное — не дать коду уйти на чужой адрес.

### `exchange` Обмен кода на токен

`client → idp` · `attack` · `without-defence`
Сообщение: code → токен · Итог: вошёл как Анна

```http
POST /token

grant_type=authorization_code
&code=⟦SplxlO…⟧
```

#### Просто

Фотопечать меняет код на токен у сервиса входа. Код настоящий, приложение настоящее — сервис
выдаёт **токен Анны**. Атакующий оказывается в аккаунте Анны на Фотопечати: её фото, адрес, заказы.

#### По шагам

Сервис входа проверил, что код выдан этому приложению и ещё не использован. Чей браузер начинал
вход, он не проверяет.

#### Глубже

RFC 6749 (раздел 4.1.3) требует ещё одну проверку: `redirect_uri` при обмене должен совпасть с
тем, что был в запросе на вход. Она бы тоже поймала атаку, но RFC 9700 отмечает, что сервисы
часто её пропускают. Против кражи и подмены кода в целом RFC 9700 (раздел 2.1.1) требует PKCE от
публичных приложений и рекомендует его остальным.

### `error` Ошибка вместо перенаправления

`idp → user` · `safe` · `with-defence`
Сообщение: неверный адрес · Итог: код не выдан

```http
HTTP/1.1 400 Bad Request
```

#### Просто

Сервис входа показывает Анне ошибку: **адрес возврата не совпадает**. Никуда её не
перенаправляет, код не создаёт.

#### По шагам

Атакующему нечего красть: ни кода, ни перенаправления на его сайт. Анна видит странную ошибку и
может об этом сообщить.

#### Глубже

RFC 6749 (раздел 4.1.2, ответ с ошибкой): при неверном адресе возврата сервису входа следует
сообщить об ошибке владельцу аккаунта, и он не должен автоматически перенаправлять браузер на этот
адрес.

## Как защититься

- **Точное сравнение redirect_uri.** Сервис входа сверяет адрес возврата с зарегистрированным
  целиком, без шаблонов и сравнения по началу. Это главная защита.
- **PKCE для всех приложений.** Приложение отправляет хеш одноразового секрета при входе и сам
  секрет при обмене кода. Код, утёкший из настоящего входа, без секрета бесполезен. RFC 9700
  требует PKCE от публичных приложений и рекомендует остальным. От подменённой ссылки, как в этом
  уроке, он спасает не всегда, поэтому точное сравнение адреса обязательно.
- **Проверка redirect_uri при обмене кода.** Адрес при обмене должен совпасть с адресом из
  запроса на вход.
- **state против CSRF.** Приложение кладёт в запрос на вход случайный `state`, привязанный к
  браузеру пользователя, и сверяет его при возврате (RFC 6749, раздел 10.12). PKCE тоже защищает от
  CSRF.
- **Никаких открытых перенаправлений.** Ни приложение, ни сервис входа не пересылают браузер на
  любой адрес из параметра запроса: через такой адрес код тоже утекает.
- **Код короткий и одноразовый.** RFC 6749 советует срок жизни кода не больше 10 минут; второй
  раз код не принимается.
