## Шаги

### `header` Заголовок с хвостом

`attacker → server` · `attack`
Сообщение: GET /status · Итог: принят как обычный запрос

```http
GET /cgi-bin/status.cgi
User-Agent: () { :;}; ⟦echo hacked⟧
```

#### Просто

На сайте есть старая страница состояния, её делает маленький скрипт. Хакер открывает её, но в
поле, где браузер называет себя, пишет **странную строку**: скобки, фигурные скобки, точка с
запятой, а в конце команда.

#### По шагам

Запрос обычный: открыть `/cgi-bin/status.cgi`. Подвох в заголовке `User-Agent`. Начало строки
похоже на описание пустой функции, а после неё стоит команда. Серверу заголовок неинтересен, он
его не проверяет.

#### Глубже

Строку можно положить в любой заголовок, который сервер передаст скрипту: `User-Agent`, `Cookie`,
`Referer`. Входа и действий человека не нужно, поэтому в векторе CVSS `PR:N` и `UI:N`. Это
частый пробный запрос: по ответу видно, выполнилась ли команда из хвоста.

### `env` Заголовок становится переменной

`server → bash` · `attack` · `without-defence`
Сообщение: запуск скрипта · Итог: заголовок в переменной

```text
HTTP_USER_AGENT=() { :;}; ⟦echo hacked⟧
```

#### Просто

Чтобы ответить, сервер **запускает скрипт** и передаёт ему данные запроса. Каждый заголовок он
кладёт в отдельную **переменную окружения** — так устроен старый способ запуска скриптов CGI.

#### По шагам

Заголовок `User-Agent` превращается в переменную `HTTP_USER_AGENT` с тем же значением, знак в
знак. Скрипт написан для Bash, поэтому сервер запускает Bash и отдаёт ему все переменные.

#### Глубже

Правило задаёт RFC 3875 (CGI 1.1), раздел 4.1.18: имя заголовка переводится в верхний регистр,
дефисы заменяются подчёркиванием, впереди ставится `HTTP_`. Значит, содержимое переменной целиком
выбирает тот, кто прислал запрос. Само по себе это не ошибка: переменная — просто текст. Беда в
том, как с этим текстом обошёлся Bash.

### `parse` Bash выполняет хвост

`bash → bash` · `attack` · `without-defence`
Сообщение: разбор переменных · Итог: команда из хвоста выполнена

```text
() { :;};      ← похоже на функцию: Bash её «импортирует»
⟦echo hacked⟧    ← хвост: Bash выполняет и его
```

#### Просто

Bash при запуске просматривает переменные. Значение, похожее на **функцию**, он принимает за
функцию и разбирает. Но ошибка в Bash заставляла его разбирать и выполнять **всё, что стоит
после** функции. Команда хакера срабатывает ещё до начала скрипта.

#### По шагам

Bash умеет передавать функции дочерним процессам через переменные окружения. Увидев значение,
которое начинается с `() {`, он читал его как описание функции. Функция кончалась на `}`, а
разбор шёл дальше, и команды после неё выполнялись сразу.

#### Глубже

NVD: GNU Bash до версии 4.3 включительно обрабатывает строки в конце описания функции в
переменных окружения, и это позволяет выполнить свой код. Класс ошибки — CWE-78, внедрение
команд ОС. CISA в бюллетене TA14-268A называет уязвимыми версии от 1.14 до 4.3: ошибка прожила
в Bash много версий. Исправление вышло неполным: остаток получил отдельный номер
CVE-2014-7169, за ним последовали и другие. CISA советовала ставить все исправления по шести
номерам этой группы.

### `run` Команды хакера на сервере

`bash → attacker` · `attack` · `without-defence`
Сообщение: обратное подключение · Итог: сервер под контролем

#### Просто

Вместо безобидного `echo` хакер мог написать любую команду. Она выполняется **с правами
веб-сервера**: например, открывает хакеру связь, и сервер сам ждёт его команд.

#### По шагам

Хакер получает командную строку на сервере. Он читает файлы сайта, ставит свои программы,
ищет пароли и путь во внутреннюю сеть.

#### Глубже

Базовая оценка в NVD — 9.8 из 10 по CVSS 3.1: атака по сети, простая, без прав и без участия
человека, страдают конфиденциальность, целостность и доступность. CISA называла и другие пути
к той же ошибке: обход `ForceCommand` в OpenSSH и клиенты DHCP. В ATT&CK это техника T1190 —
взлом приложения, открытого в интернет. CISA внесла CVE-2014-6271 в каталог KEV 28 января 2022
года — через семь с лишним лет после выхода исправления.

### `patched` Обновлённый Bash

`server → bash` · `attack` · `with-defence` · `stopped`
Сообщение: запуск скрипта · Итог: хвост не выполнен, атака не сработала

```text
HTTP_USER_AGENT=() { :;}; ⟦echo hacked⟧
```

#### Просто

Переменная та же, но Bash **обновлён**. Теперь он не выполняет то, что стоит после функции, и
чужую строку из обычной переменной функцией не считает.

#### По шагам

Скрипт запускается и получает переменную `HTTP_USER_AGENT` как простой текст. Команда из хвоста
не выполняется. Скрипт делает свою работу: собирает состояние сервера.

#### Глубже

Первое исправление закрыло не всё: остаток ошибки получил номер CVE-2014-7169, поэтому
обновляться пришлось не один раз. Но главный урок шире: Bash не нужен там, где сервер запускает
программы по запросам из интернета. Сайт без CGI на Bash этой атаке вообще не подвержен.

### `output` Обычный ответ скрипта

`bash → server` · `safe` · `with-defence`
Сообщение: статус: OK · Итог: страница собрана

#### Просто

Скрипт отдаёт серверу то, ради чего его и запускали: короткую сводку о состоянии сайта.

#### По шагам

Сервер получает вывод скрипта и превращает его в страницу. Строка из заголовка ни на что не
повлияла.

#### Глубже

В журнале сервера остаётся запрос со строкой `() {` в заголовке. По таким строкам видно, кто и
когда пробовал атаку, даже если она не удалась.

### `answer` Хакер видит обычную страницу

`server → attacker` · `safe` · `with-defence`
Сообщение: 200 OK · Итог: атака не удалась

#### Просто

Хакер получает обычную страницу состояния, как любой посетитель. Его команда не сработала.

#### По шагам

Ответ такой же, как на запрос без странного заголовка. Сервер под контролем владельца.

#### Глубже

Shellshock показывает, почему старый код опасен: ошибка сидела в Bash с версии 1.14, а старые
скрипты CGI и устройства, которые редко обновляют, работают годами. Обновление закрывает
уязвимость только там, где его поставили: в KEV эта ошибка попала уже в 2022 году.

## Как защититься

- **Обновить Bash.** Главная защита: поставить исправленную версию из обновлений системы. Одного
  первого исправления мало — нужны все исправления по этой группе ошибок.
- **Знать, где он стоит.** Bash входит в Linux, macOS и многие другие UNIX-подобные системы, в
  том числе внутри устройств. Составьте список систем и спросите поставщиков об обновлениях.
- **Не запускать оболочку по запросу из интернета.** Не пишите скрипты CGI на Bash и не
  вызывайте оболочку из веб-приложения. Чем меньше программ видит данные запроса, тем меньше
  поверхность атаки.
- **Не доверять заголовкам.** Всё, что прислал посетитель, включая заголовки, — данные, а не
  команды.
- **Искать следы.** Строки `() {` в журналах сервера показывают попытки атаки; признаки успешного
  взлома нужно проверять отдельно.
