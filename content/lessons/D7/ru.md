## Шаги

### `form` Обычная правка профиля

`attacker → server` · `legit`
Сообщение: имя и город · Итог: сохранено

```http
PATCH /api/profile
Host: shop.example

{"name": "Олег", "city": "Тверь"}
```

#### Просто

Атакующий зарегистрирован в магазине как **обычный покупатель**. Он открывает профиль, меняет имя
и город и нажимает «Сохранить».

#### По шагам

Страница профиля отправляет на сервер JSON с двумя полями: `name` и `city`. Сервер сохраняет их,
всё работает, как задумано.

#### Глубже

Атакующий смотрит в инструментах разработчика браузера, что именно уходит на сервер. Запрос
можно повторить и изменить вручную: сервер видит только байты запроса, а не кнопки формы.

### `extra` Лишнее поле в JSON

`attacker → server` · `attack` · `without-defence`
Сообщение: ещё isAdmin: true · Итог: принято

```http
PATCH /api/profile

{"name": "Олег", "city": "Тверь", ⟦"isAdmin": true⟧}
```

#### Просто

Атакующий дописывает в тот же запрос поле, которого **нет в форме**: `"isAdmin": true`. Имя он
угадал: такие поля часто называются одинаково.

#### По шагам

Подсказки бывают и в ответах самого сервера: если `GET /api/profile` возвращает весь объект
пользователя вместе с `isAdmin: false`, имя поля уже известно.

#### Глубже

OWASP называет это **mass assignment**, а у разных фреймворков встречаются и другие имена:
autobinding и object injection. В OWASP API Security Top 10 2023 эта ошибка вошла в API3 «Broken
Object Property Level Authorization»: пользователь меняет свойство объекта, к которому у него не
должно быть доступа.

### `bind` Сервер копирует всё подряд

`server → db` · `attack` · `without-defence`
Сообщение: isAdmin = true · Итог: сохранено

```js
const user = await db.users.find(me);
Object.assign(user, ⟦request.body⟧);
await user.save();
```

#### Просто

Сервер **не выбирает** поля: он берёт весь присланный JSON и переносит его в объект пользователя.
Вместе с именем и городом в базу уходит `isAdmin = true`.

#### По шагам

Код удобен: одна строка вместо перечня полей. Программист думал, что придут только поля формы, но
клиент присылает что захочет.

#### Глубже

MITRE описывает это как CWE-915: продукт получает данные, которые задают сразу несколько полей
объекта, и не проверяет, какие из них можно менять. Многие фреймворки умеют сами связывать
параметры запроса с объектом; без явного списка разрешённых полей это связывание доступно
каждому.

### `admin` Вход в админку

`attacker → server` · `attack` · `without-defence`
Сообщение: GET /admin · Итог: вошёл как админ

```http
GET /admin
Host: shop.example
```

#### Просто

Атакующий открывает **панель администратора**. Сервер смотрит в базу, видит `isAdmin = true` и
пускает его.

#### По шагам

Теперь он видит заказы, адреса и телефоны всех покупателей и может менять цены. Ни пароль, ни
чужая учётная запись не понадобились.

#### Глубже

Тот же приём работает с любым полем, которое не должен трогать пользователь: баланс, скидка,
статус «проверен», владелец записи. OWASP относит CWE-915 к A08:2021 «Software and Data Integrity
Failures»: сервер доверяет данным, целостность которых не проверил.

### `allow` Только разрешённые поля

`attacker → server` · `attack` · `with-defence` · `stopped`
Сообщение: ещё isAdmin: true · Итог: атака не сработала

```js
const { name, city } = request.body;
// ⟦isAdmin⟧ сервер не читает
```

#### Просто

Сервер берёт из запроса **только** `name` и `city` — по белому списку. Поле `isAdmin` он просто
не читает.

#### По шагам

Лишнее поле не вызывает ошибки, оно молча отбрасывается. Можно и отвечать ошибкой на любое
неизвестное поле: так попытку легче заметить в журнале.

#### Глубже

OWASP советует не связывать ввод напрямую с объектами базы, а заводить отдельный объект для
передачи данных (DTO), где есть только поля, которые пользователь вправе менять. Второй вариант —
явный белый список полей при связывании. Чёрный список «всё, кроме isAdmin» хуже: новое
чувствительное поле, добавленное через год, окажется открытым.

### `save-safe` В базу уходят имя и город

`server → db` · `safe` · `with-defence`
Сообщение: name, city · Итог: isAdmin не тронут

```sql
UPDATE users SET name = ?, city = ? WHERE id = ?
```

#### Просто

В базу записываются **только имя и город**. У атакующего по-прежнему `isAdmin = false`.

#### По шагам

Права меняет только отдельный запрос администратора, и сервер проверяет, что его прислал
администратор.

#### Глубже

Список полей, которые можно менять, задаёт сервер, а не клиент. Его стоит держать рядом с
проверкой прав: кто какое поле может трогать. Тогда новая колонка в таблице не становится
доступной для правки сама собой.

## Как защититься

- **Белый список полей.** Сервер явно перечисляет, что можно менять в каждом запросе, и игнорирует
  или отклоняет остальное.
- **Отдельный объект для ввода.** Запрос связывается с DTO, где есть только редактируемые поля, а
  не с объектом базы данных.
- **Не чёрный список.** Запрет отдельных полей забывают обновить, когда в модели появляется новое.
- **Права проверяются на сервере.** Роль, баланс, владелец записи меняются только отдельными
  действиями с проверкой, кто их просит.
- **Не отдавать лишнего.** Ответ API содержит только нужные клиенту поля: так имена внутренних
  полей не подсказывают, что дописать.
