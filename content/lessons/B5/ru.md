## Шаги

### `cart` Корзина в cookie

`server → attacker` · `legit` · `without-defence`
Сообщение: cart: rO0AB... · Итог: объект корзины у посетителя

```http
Set-Cookie: cart=rO0ABXNyAARDYXJ0...
```

#### Просто

Магазин не хранит корзину у себя. Он **упаковывает объект «Корзина»** из своей программы в строку
и отдаёт её браузеру. Со следующим запросом браузер вернёт строку, и сервер распакует корзину
обратно.

#### По шагам

Сервер превращает объект в байты встроенным способом языка (здесь Java) и кодирует их в Base64.
Получается cookie `cart`. Браузер честно прикладывает её к каждому запросу.

#### Глубже

Упаковка объекта в байты называется сериализацией, распаковка — десериализацией. OWASP пишет, что
данные Java-сериализации в Base64 начинаются с `rO0`: так их легко узнать. Встроенные форматы
умеют больше, чем JSON: в них записано и *какого класса* объект.

### `cart-json` Корзина как данные

`server → attacker` · `legit` · `with-defence`
Сообщение: cart: JSON · Итог: только номера товаров

```text
cart = {"items": [17, 42]}
```

#### Просто

В режиме защиты сервер отдаёт корзину **просто как список товаров**, а не как объект программы.
В нём только числа и строки, никаких классов.

#### По шагам

Сервер записывает корзину в JSON: номера товаров в списке. Из такого текста можно получить только
числа, строки и списки.

#### Глубже

OWASP советует для данных, которые уходят к посетителю и возвращаются, брать простой стандартный
формат вроде JSON, а не встроенный формат объектов. Объект `Cart` сервер потом собирает сам, по
своим правилам, и проверяет каждое значение.

### `forge` Подделка

`attacker → attacker` · `attack`
Сообщение: объект чужого класса · Итог: готова поддельная строка

```text
вместо Cart:
⟦объект класса из библиотеки сервера,
 в поле — команда⟧
```

#### Просто

Атакующий собирает свою строку. Внутри не корзина, а **объект другого класса**, который есть в
библиотеках сервера. Своего кода он не пишет: он только выбирает классы и заполняет их поля.

#### По шагам

Атакующий знает, какие популярные библиотеки стоят у сайтов на Java. В некоторых есть классы,
методы которых при распаковке вызывают друг друга. Он выстраивает их в цепочку, а в поле
последнего кладёт команду.

#### Глубже

Такие классы называют гаджетами, а их связку — цепочкой гаджетов. По MITRE, гаджеты часто
находятся в библиотеках и срабатывают сами во время десериализации. Новые цепочки находят
постоянно.

### `send` Поддельная корзина

`attacker → server` · `attack`
Сообщение: cookie cart с подделкой · Итог: принято

```http
Cookie: cart=⟦rO0ABXNy...подделка⟧
```

#### Просто

Атакующий отправляет обычный запрос, но в cookie `cart` подставляет свою строку. Для сервера это
выглядит как корзина, которую он сам выдал.

#### По шагам

Cookie хранится в браузере, а значит, посетитель может заменить её чем угодно. Сервер получает
строку, не зная, кто её собрал.

#### Глубже

Всё, что приходит от клиента, — ввод посетителя: поля формы, заголовки, cookie, скрытые поля.
Сервер не может знать, что cookie не меняли, если сам этого не проверит.

### `revive` Сервер оживляет объект

`server → server` · `attack` · `without-defence`
Сообщение: readObject() · Итог: атака

```text
readObject(cart)
→ создан ⟦класс из библиотеки⟧
→ вызван его метод → следующий ...
```

#### Просто

Сервер распаковывает строку и **создаёт объекты тех классов, что в ней названы**. При сборке
объекты сами вызывают свои методы. Цепочка срабатывает раньше, чем сервер успевает проверить,
корзина ли это.

#### По шагам

Код сайта вызывает `readObject` и только потом приводит результат к типу `Cart`. Но к этому моменту
поддельные объекты уже собраны и их методы уже выполнились.

#### Глубже

Это ошибка CWE-502: сервер десериализует данные, не убедившись, что им можно верить. Встроенный
формат позволяет присланным данным выбрать, объекты каких классов будут созданы. Последствия, по
OWASP, — от отказа в обслуживании и обхода контроля доступа до выполнения чужого кода.

### `exec` Команда запущена

`server → os` · `attack` · `without-defence`
Сообщение: команда · Итог: код атакующего выполнен

```text
⟦команда из поддельного объекта⟧
```

#### Просто

Последнее звено цепочки просит систему запустить команду. Система запускает её **от имени
магазина**. Атакующий выполнил на сервере свою команду.

#### По шагам

Команда работает с правами сайта: читает файлы, открывает соединения, ставит программы. Ответ
атакующему не нужен: команда уже выполнилась.

#### Глубже

Это удалённое выполнение кода, хотя атакующий не прислал ни строчки кода, только данные. Поэтому
такую ошибку трудно заметить: в запросе нет ни скрипта, ни команды оболочки в привычном виде.

### `parse` Чтение JSON

`server → server` · `attack` · `with-defence` · `stopped`
Сообщение: это не JSON корзины · Итог: отклонено, атака не сработала

```text
разбор JSON(⟦rO0ABXNy...⟧) → ошибка
```

#### Просто

Теперь сервер читает корзину как JSON. В JSON нет классов, и создать объект по имени из присланных
данных нельзя. Подделка — не JSON, и сервер её отбрасывает. Атака останавливается здесь.

#### По шагам

Разбор JSON даёт только числа, строки и списки. Строка атакующего не разбирается, и сервер не
создаёт ни одного объекта.

#### Глубже

Если от встроенного формата уйти нельзя, OWASP и MITRE советуют подписывать данные (например,
HMAC) и не распаковывать то, у чего подпись не сходится, а также ограничивать классы белым списком
(в Java — фильтры сериализации). Но белый список классов в одиночку не спасает: новые гаджеты
находят постоянно. И сама библиотека JSON не должна создавать классы по имени из данных: у
некоторых такая возможность есть, её держат выключенной.

### `refuse` Пустая корзина

`server → attacker` · `safe` · `with-defence`
Сообщение: корзина сброшена · Итог: атака не удалась

#### Просто

Сервер считает корзину испорченной и выдаёт пустую. Атакующий получил пустую корзину, и только.

#### По шагам

Сервер отвечает обычной страницей и новой cookie с пустым списком товаров.

#### Глубже

Сервер даже не пытался понять, что было внутри подделки: для него это просто неверный текст. Ни
один чужой класс не создан, ни один метод не вызван.

## Как защититься

- **Не принимать объекты от посетителя.** Для данных, которые уходят клиенту и возвращаются,
  берите простой формат вроде JSON и собирайте объекты сами, проверяя значения.
- **Подпись, если без формата не обойтись.** Сервер подписывает данные (например, HMAC) и не
  распаковывает то, у чего подпись не сходится.
- **Белый список классов.** В Java — фильтры сериализации со списком разрешённых классов и
  пределами размера. Это слой защиты, а не замена первым двум.
- **Меньше лишних классов.** Не держите в приложении, которое разбирает чужие данные, библиотеки и
  классы, которые ему не нужны.
- **Следить за известными гаджетами.** OWASP (в разделе про .NET) советует знать известные
  опасные классы платформы и особенно следить, где десериализация может их создать.
